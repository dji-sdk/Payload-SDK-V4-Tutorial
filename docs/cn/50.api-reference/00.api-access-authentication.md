负载设备接入飞机端 broker 是收发所有业务报文的前提。本章节介绍负载设备安全接入（Secure Access）MQTT 服务器的底层协议，涵盖三部分内容：接入所使用的连接参数、两次接入鉴权的报文构造规则，以及业务报文的完整性校验机制。

:::tip 说明：
PSDK 中的 C 接口是对本章节 MQTT 协议的封装。使用 PSDK 开发时，无需直接操作 MQTT 报文；如需自行实现协议对接，或对接入过程进行调试验证，可参照本章节的协议定义。功能介绍与 C 接口调用示例详见 <a href="../function-set/access-authentication.html" target="_blank" rel="noopener noreferrer">功能集合-接入与鉴权</a>。
:::

## 连接概述

接入过程需依次建立两条连接，并分别完成一次鉴权：

| 连接 | 端口 | 传输通道 | 鉴权方式 | 用途 |
|:---|:---|:---|:---|:---|
| 连接一 | 8883 | TLS | 基于应用凭据 | 在 TLS 加密通道内校验应用凭据，并导出与本次连接绑定的密钥材料；完成后断开。 |
| 连接二 | 1883 | 普通 MQTT | 基于 token | 使用连接一导出的密钥材料计算 token 接入，建立业务长连接；后续所有业务报文复用此连接。 |

:::warning 注意：
TLS 仅用于加密传输通道并校验 broker 的服务器证书，其本身不构成对负载身份的鉴权。对负载身份的鉴权由上表所列的两次鉴权完成。
:::

两次连接均由负载向飞机发起，MQTT 连接标识 `{client_id}` 均为负载设备序列号（`device_sn`），QoS 均为 0。

## 连接参数

接入所需的参数如下。其中 `app_id`、`app_name`、`app_key`、`app_license` 为应用凭据，获取方式详见 <a href="../payload-quick-start/quick-demo/raspberry-pi.html#获取应用信息" target="_blank" rel="noopener noreferrer">获取应用信息</a>；其余为设备与连接信息。

| 参数 | 类型 | 必填 | 含义与取值 |
|:---|:---|:---|:---|
| app_id | string | 是 | 应用 ID，取平台分配的字符串。 |
| app_name | string | 否 | 应用名称，即创建应用时填写的名称（如 `psdkappfortest`）。服务器据此识别应用身份，建议填写。 |
| app_key | string | 是 | 应用密钥。 |
| app_license | string | 是 | 应用授权码。 |
| device_sn | string | 是 | 负载设备序列号，由负载开发者自定义（**非飞机 SN**），用于标识接入的负载，其同时作为 MQTT 连接标识 `{client_id}` 及各业务 Topic 中的 `{client_id}`。<br>格式要求：由数字、字母、下划线（`_`）组成，长度不超过 64 个字符；每个负载客户端需使用各自不同的 `device_sn`。 |
| broker_address | string | 是 | 飞机端 broker 的地址。按飞机型号取值，例如 Matrice 5TD 为 `192.168.100.3`。 |
| broker_port_tls | int | 是 | TLS 连接（连接一）端口，取值为 `8883`。 |
| broker_port | int | 是 | 普通 MQTT 连接（连接二）端口，取值为 `1883`。 |
| ca_cert_path | string | 是 | CA 证书（`ca.crt`）路径，用于校验 broker 的服务器证书。证书获取方式详见 <a href="../payload-quick-start/quick-demo/raspberry-pi.html#下载证书" target="_blank" rel="noopener noreferrer">下载证书</a>。 |

## 连接一：基于应用凭据的鉴权

负载通过 TLS 连接 broker 的 `8883` 端口，MQTT 用户名与密码按下列规则构造。鉴权通过后，从 TLS 会话导出 32 字节密钥材料（下称 `hmac_key`），供连接二使用；随后断开该连接。
```text
username: {app_id}:{app_name}_psdk_{device_sn}    # 无 app_name 时为 {app_id}_psdk_{device_sn}
password: {app_key}_{app_license}_{timestamp_ms}  # timestamp_ms 为客户端毫秒时间戳，用于防重放
```

`hmac_key` 通过 TLS 密钥导出（RFC 5705 keying material）得到，与本次 TLS 会话绑定。

## 连接二：基于 token 的鉴权

负载通过普通 MQTT 连接 broker 的 `1883` 端口，MQTT 用户名与密码按下列规则构造：

```text
username: token:{hex(HMAC-SHA256(hmac_key, device_sn))}
password:                                               # 空
```

连接二建立后即为业务长连接，后续所有业务 Topic 的收发均复用此连接。

## 业务报文完整性校验

连接二建立后，负载发布（PUBLISH）的每条业务报文，需在原始 payload 末尾追加毫秒时间戳与 HMAC 签名，供服务器校验报文的完整性与时效性。订阅（SUBSCRIBE）接收的报文不包含该结构。

:::tip 说明：
该机制用于**防篡改**（报文在传输途中被修改会导致 HMAC 校验失败）与**防重放**（旧报文因时间戳过期而被拒绝）。
:::

发布报文的字节布局为：**原始 payload ‖ 8 字节时间戳（大端）‖ 32 字节 HMAC**。各部分说明如下：

- `‖` 表示字节拼接（首尾相接）。
- **8 字节时间戳**：发送时刻的毫秒时间，采用大端序（高位字节在前）存储。
- **32 字节 HMAC**：消息认证码，以密钥 `hmac_key`（连接一鉴权时导出）对前面的「payload ‖ 时间戳」做 HMAC-SHA256 计算得出。

```text
最终发布字节 = payload || ts_be8 || HMAC32
其中  HMAC32 = HMAC-SHA256(key = hmac_key, message = payload || ts_be8)
```

以业务 JSON `{"seq":1,"method":"efts_get_fts_trigger_status","data":{}}`、发布时刻 `ts = 1753689600000`（0x0001987B8E5A6800）为例，实际发布到 MQTT 的报文（以十六进制展示尾部追加部分）为：

```text
[payload 原文 53 字节]
7B 22 73 65 71 22 3A 31 ... 7D          # {"seq":1,...,"data":{}}
[+ 8 字节时间戳，大端]
00 01 98 7B 8E 5A 68 00                  # ts = 1753689600000
[+ 32 字节 HMAC-SHA256(hmac_key, payload||ts)]
a3 f1 c9 ... （共 32 字节）              # 服务器用同一 hmac_key 复算比对
```

服务器收到后，按同样规则用 `hmac_key` 对「payload ‖ ts」复算 HMAC，并与报文末尾的 32 字节比对：一致则说明报文完整、未被篡改；同时校验时间戳，超出有效时间窗口的报文（如被录制后重放）将被拒绝。
