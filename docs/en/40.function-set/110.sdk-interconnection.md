## Overview

:::warning Warning:
The data plane of the MOP data channel is based on POSIX TCP sockets and supports only Linux. It does not apply to RTOS builds. Before use, confirm that the payload runtime environment is Linux and that the aircraft firmware supports MOP channels.
:::

SDK Interconnection is used to establish a communication link between a payload device and a mobile MSDK, an onboard OSDK, or another payload PSDK device. MOP is the data channel feature used to create high-speed channels and transmit large volumes of application data.

The MOP data channel separates the control plane from the data plane. The control plane negotiates the target device, channel parameters, and channel status over MQTT. The data plane is a TCP connection established by the payload based on the returned IP address and port, and does not go through MQTT.

:::tip Note:
- The C interfaces in PSDK encapsulate the underlying MQTT protocol. Developers can complete protocol interactions by calling the C interfaces directly, without manually constructing MQTT messages. For MQTT payload structures and field definitions, see <a href="../api-reference/api-sdk-interconnection.html" target="_blank" rel="noopener noreferrer">Protocol Reference - SDK Interconnection</a>.
- Before using this feature, the payload device must first complete access and authentication. For details, see <a href="access-authentication.html" target="_blank" rel="noopener noreferrer">Access and Authentication</a>.
:::

## Basic Concepts

### Terminology

**Control Plane**

The channel that negotiates channel parameters and status via the MQTT protocol, carrying the enable/disable channel commands and channel status pushes.

**Data Plane**

The TCP channel that carries the actual application data. The payload establishes a TCP connection based on the IP address and port returned by the control plane, and then sends and receives data over this connection. The data does not go through MQTT.

**Channel Role**

The connection role of the two ends of the channel. `ROLE_SERVER` listens and waits for the peer to connect, and `ROLE_CLIENT` actively connects to the peer.

**Transmission Type**

The transmission type of the data plane. `RELIABILITY_RELIABLE` is reliable transmission, and `RELIABILITY_UNRELIABLE` is unreliable transmission.

### Channel Establishment Sequence

The payload drives the control plane and manages the data plane throughout the channel lifecycle. The typical sequence is as follows:

1. **Enable channel**: The payload calls `MopChannel_Enable()`, and the aircraft returns the channel status `state` and the TCP data plane endpoint `ip`/`port` in the response.
2. **Establish data plane**: The payload establishes a TCP connection based on `ip`/`port`.
3. **Wait for ready**: The aircraft issues `CHANNEL_STATE_ACTIVE` via a channel status push, indicating the data plane is ready, and the payload can start TCP sending/receiving.
4. **Disable channel**: The payload calls `MopChannel_Disable()`, and after the aircraft acknowledges, it issues `CHANNEL_STATE_CLOSED` via a channel status push, based on which the payload safely closes the TCP socket.

:::warning Warning:
- The channel ID is not restricted to a fixed value range; communication can be established as long as both ends agree to use the same channel number.
- The payload should register the channel status callback `MopChannel_OnChannelEvent()` first, and then call `MopChannel_Enable()`, to avoid missing the ACTIVE status.
- After receiving `CHANNEL_STATE_CLOSED`, the TCP socket should be safely closed; if CLOSED is received while waiting for ACTIVE, it usually indicates that the peer device is not ready.
- The channel status callback is triggered on a background thread. Synchronous APIs (such as `MopChannel_Enable()` / `MopChannel_Disable()`) should not be called within the callback, nor should the client be destroyed; TCP sending/receiving should be performed in a separate thread.
:::

## Feature Introduction

:::warning Warning:
The following code is for reference only and demonstrates the call flow and implementation of each feature. Developers can adapt it based on the hardware characteristics and application scenarios of the payload device.
:::

### Create Client

Create a MOP channel client on the established MQTT session `session`; subsequent interfaces are all called through this client.

```c
MopChannel_Client_t *client = MopChannel_CreateClient(session);
```

### Receive Channel Status

Register a callback to receive the channel status pushed by the aircraft. The callback is triggered when the channel status changes. The parameter `push` points to the decoded status push structure. Register the callback first, then enable the channel, to avoid missing the ACTIVE status. For the corresponding MQTT protocol, see <a href="../api-reference/api-sdk-interconnection.html#channel-status-push" target="_blank" rel="noopener noreferrer">Channel Status Push</a>.

```c
static void on_channel_event(void *user, const T_ChannelEventPush *push)
{
    if (!push) return;
    if (push->state == CHANNEL_STATE_ACTIVE) {
        /* Data plane is ready, notify the send/receive thread to start TCP read/write */
    } else if (push->state == CHANNEL_STATE_CLOSED) {
        /* Channel closed, safely close the TCP socket */
    }
}

T_ThingModelReturnCode rc = MopChannel_OnChannelEvent(client, on_channel_event, NULL);
if (rc != THING_MODEL_RC_OK) {
    USER_LOG_ERROR("register channel event callback failed: rc=%d", rc);
}
```

Field descriptions of the push structure `T_ChannelEventPush`:

| Field | Type | Description |
|------|------|------|
| channel_id | uint32_t | Channel ID; communication can be established as long as both ends agree to use the same channel number |
| state | E_ChannelState | Channel status.<ul><li>CHANNEL_STATE_ACTIVE (1): Data plane is ready</li><li>CHANNEL_STATE_CLOSED (2): Channel closed, the socket should be safely closed</li></ul> |

:::warning Warning:
The callback is triggered on a background thread. Synchronous APIs should not be called within the callback, nor should the client be destroyed; TCP sending/receiving and time-consuming logic should be handed off to other threads.
:::

### Enable Channel

Enable the data channel; the aircraft returns the TCP data plane endpoint in the response. Before calling, first initialize the request structure with `MopChannel_InitMopEnableRequest()`, and set the role, transmission type, channel ID, target device type, and target address. For the corresponding MQTT protocol, see <a href="../api-reference/api-sdk-interconnection.html#enable-channel" target="_blank" rel="noopener noreferrer">Enable Channel</a>.

```c
T_MopEnableRequest req;
MopChannel_InitMopEnableRequest(&req);
req.role               = ROLE_CLIENT;
req.reliability        = RELIABILITY_RELIABLE;
req.channel_id         = 49153;
req.target_device_type = TARGET_DEVICE_TYPE_PSDK;
req.target_address     = 1;   /* In client mode, this is the target payload position 1/2/3 */

T_MopEnableReply reply;
MopChannel_InitMopEnableReply(&reply);
T_ThingModelReturnCode rc = MopChannel_Enable(client, &req, &reply, 5000);
if (rc == THING_MODEL_RC_OK && reply.result == 0) {
    USER_LOG_INFO("enable ok: state=%s ip=%s port=%u",
                  reply.state, reply.ip, reply.port);
    /* Establish a TCP connection based on reply.ip / reply.port */
} else {
    USER_LOG_ERROR("enable failed: rc=%d result=%d msg=%s",
                   rc, reply.result, reply.result_message);
}
MopChannel_FreeMopEnableReply(&reply);
```

Field descriptions of the request structure `T_MopEnableRequest`:

| Field | Type | Description |
|------|------|------|
| role | E_Role | Channel role.<ul><li>ROLE_SERVER (0): Listens and waits for the peer to connect</li><li>ROLE_CLIENT (1): Actively connects to the peer</li></ul> |
| reliability | E_Reliability | Transmission type.<ul><li>RELIABILITY_RELIABLE (0): Reliable transmission</li><li>RELIABILITY_UNRELIABLE (1): Unreliable transmission</li></ul> |
| channel_id | uint32_t | Channel ID; communication can be established as long as both ends agree to use the same channel number |
| target_device_type | E_TargetDeviceType | Target device SDK type.<ul><li>TARGET_DEVICE_TYPE_MSDK (1): Mobile</li><li>TARGET_DEVICE_TYPE_OSDK (2): Onboard</li><li>TARGET_DEVICE_TYPE_PSDK (3): Payload</li></ul> |
| target_address | uint32_t | Target address.<ul><li>client mode: Target payload position 1, 2, 3</li><li>server mode: Fixed to 0</li></ul> |

Field descriptions of the reply structure `T_MopEnableReply`:

| Field | Type | Description |
|------|------|------|
| result | int32_t | Processing result, 0 indicates success |
| result_message | char * | Result description information |
| channel_id | uint32_t | Channel ID |
| state | char * | Channel status, "listening" on success |
| ip | char * | TCP data plane endpoint IP address |
| port | uint32_t | TCP data plane endpoint port |

:::tip Note:
`T_MopEnableReply` contains `char *` fields, which must be released by calling `MopChannel_FreeMopEnableReply()` after use. After enabling successfully, first establish a TCP connection based on `ip`/`port`, then wait for the channel status push `CHANNEL_STATE_ACTIVE` to confirm the data plane is ready.
:::

### Disable Channel

Disable the data channel. After the aircraft acknowledges, it issues `CHANNEL_STATE_CLOSED` via a channel status push, based on which the payload safely closes the TCP socket. For the corresponding MQTT protocol, see <a href="../api-reference/api-sdk-interconnection.html#disable-channel" target="_blank" rel="noopener noreferrer">Disable Channel</a>.

```c
T_MopDisableRequest req;
MopChannel_InitMopDisableRequest(&req);
req.channel_id = 49153;

T_Placeholder resp;
memset(&resp, 0, sizeof(resp));
T_ThingModelReturnCode rc = MopChannel_Disable(client, &req, &resp, 5000);
if (rc != THING_MODEL_RC_OK) {
    USER_LOG_ERROR("disable failed: rc=%d", rc);
}
/* Close the TCP socket after receiving the channel status push CHANNEL_STATE_CLOSED */
```

Field descriptions of the request structure `T_MopDisableRequest`:

| Field | Type | Description |
|------|------|------|
| channel_id | uint32_t | The channel ID to be disabled |

:::tip Note:
The service response of disabling the channel is empty; the real close signal is issued via the channel status push `CHANNEL_STATE_CLOSED`. The payload should close the TCP socket only after receiving CLOSED, to avoid data plane residue.
:::

### Destroy Client

When the MOP channel feature is no longer used, destroy the client to release resources. Before destroying, the enabled channel should be disabled and the session disconnected first.

```c
MopChannel_DestroyClient(client);
```
