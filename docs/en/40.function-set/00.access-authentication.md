## Overview

Secure Access is required before using any service feature. The payload device must first connect to the aircraft-side broker as an MQTT client. After the connection is established, the payload can create capability clients on the session and exchange service messages.

:::tip Note:
The C interfaces in PSDK encapsulate the underlying MQTT protocol. Developers can complete protocol interactions by calling the C interfaces directly, without manually constructing MQTT messages. For MQTT connection parameters, authentication message construction rules, and field definitions, see <a href="../api-reference/api-access-authentication.html" target="_blank" rel="noopener noreferrer">Protocol Reference - Access and Authentication</a>.
:::

## Interface Overview

Secure access is completed by calling `ThingModelClientSession_Connect()`. When calling this interface, pass in an access configuration `ThingModelClientSession_Config_t`. If the call succeeds, the interface returns a session handle. You can then use this session to create capability clients and exchange messages on service topics. Before exiting, call `ThingModelClientSession_Disconnect()` to release the session.

## Access Parameters

The access parameters are the fields of the access configuration `ThingModelClientSession_Config_t`. Among them, `app_id`, `app_name`, `app_key`, and `app_license` are the application credentials; for how to obtain them, see <a href="../payload-quick-start/quick-demo/raspberry-pi.html#obtaining-application-information" target="_blank" rel="noopener noreferrer">Obtaining Application Information</a>. The rest are device and connection information.

| Field | Type | Required | Meaning and how to fill in |
|:---|:---|:---|:---|
| app_id | string | Yes | Application ID; fill in the string assigned by the platform. |
| app_name | string | No | Application name, i.e., the name entered when creating the application (such as `psdkappfortest`). The server identifies the application by this name; providing it is recommended. |
| app_key | string | Yes | Application key; keep it safe and do not hard-code it into the repository. |
| app_license | string | Yes | Application license. |
| device_sn | string | Yes | Serial number of the payload device, customized by the payload developer (**not the aircraft SN**). It identifies the connected payload and is used as both the MQTT client identifier and the `{client_id}` in each service topic.<br>Format: digits, letters, and underscores (`_`), no more than 64 characters. Each payload client must use a unique `device_sn`. |
| broker_address | string | Yes | Address of the aircraft-side broker. Fill it in according to the aircraft model; for example, Matrice 5TD is `192.168.100.3`. |
| broker_port_tls | int | Yes | Port for the TLS authentication connection; fill in `8883`. |
| broker_port | int | Yes | Port for the persistent service connection; fill in `1883`. |
| ca_cert_path | string | Yes | Path to the CA certificate (`ca.crt`), used to verify the broker's server certificate. For how to obtain the certificate, see <a href="../payload-quick-start/quick-demo/raspberry-pi.html#download-the-certificate" target="_blank" rel="noopener noreferrer">Download the Certificate</a>. |

## Call Example

The following example shows how to configure the access parameters, establish a session, and release the session.

```c
#include "thing_model_client/thing_model_client_session.h"

ThingModelClientSession_Config_t cfg = {0};
cfg.app_id          = "your_app_id";
cfg.app_name        = "your_app_name";
cfg.app_key         = "your_app_key";
cfg.app_license     = "your_app_license";
cfg.device_sn       = "your_device_sn";
cfg.broker_address  = "192.168.100.3";     /* Aircraft-side MQTT server address; fill in according to the aircraft model */
cfg.broker_port_tls = 8883;
cfg.broker_port     = 1883;
cfg.ca_cert_path    = "/path/to/ca.crt";

ThingModelClientSession_t *s = ThingModelClientSession_Connect(&cfg);
if (!s) {
    /* Access failed; query the reason via ThingModelClientSession_GetLastError() */
    return;
}

/* ... create capability clients on the session and exchange service messages ... */

ThingModelClientSession_Disconnect(s);
```

Each sample (such as EFTS under the `samples/` directory) further wraps access into `sample_session_open(&cfg)`, which internally also calls `ThingModelClientSession_Connect()`.

## Authentication Description

The access process includes two authentication steps, both handled automatically by the SDK inside `ThingModelClientSession_Connect()`. Service code does not need to participate in these steps:

1. **Application credential-based authentication**: The payload connects to broker port `8883` over TLS and authenticates with the application credentials over the encrypted channel. After authentication succeeds, the SDK exports the keying material bound to this connection and then closes the connection.
2. **Token-based authentication**: The SDK calculates a token using the keying material exported in the previous step, and then connects to broker port `1883` over plain MQTT to establish the persistent service connection. All subsequent service messages reuse this connection.

:::warning Warning:
- TLS is used only to encrypt the transport channel and verify the broker's server certificate. It does not authenticate the payload identity by itself. Payload identity authentication is completed by the two authentication steps described above.

- If access fails and returns an authentication error, check whether the application credentials (App Key / App License), device serial number, and CA certificate are correct.
:::

For the message construction rules and field definitions involved in the access process, see <a href="../api-reference/api-access-authentication.html" target="_blank" rel="noopener noreferrer">Protocol Reference - Access and Authentication</a>.
