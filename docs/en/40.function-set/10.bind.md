## Overview

:::warning Warning:
Application binding is required before using service features. When a device is unbound, the aircraft rejects service requests. After the payload connects, it should first confirm the binding status before starting features such as custom widgets and the speaker.
:::

This section describes how the payload **monitors and queries the binding status**. Application binding (Bind) confirms the authorization relationship between the payload device and the flight platform. After a device connects to MQTT, if it is not yet bound, the aircraft pushes `bind_required` through the event channel. After receiving this event, the payload can suspend subsequent service requests and guide the pilot to complete binding in DJI Assistant 2. For the binding concept and process, see <a href="../payload-quick-start/app-bind.html" target="_blank" rel="noopener noreferrer">Application Binding</a>.

The payload does not need to initiate a binding request. It only needs to subscribe to the event channel and handle binding status changes.

:::tip Note:
- The C interfaces in PSDK encapsulate the underlying MQTT protocol. Developers can complete protocol interactions by calling the C interfaces directly, without manually constructing MQTT messages. For MQTT payload structures and field definitions, see <a href="../api-reference/api-bind.html" target="_blank" rel="noopener noreferrer">Protocol Reference - Binding Status Notification</a>.
- The device must first complete access and authentication before it can connect to the broker and perform binding. For details, see <a href="access-authentication.html" target="_blank" rel="noopener noreferrer">Access and Authentication</a>.
:::

## Basic Concepts

### Terminology

**Bind**

The identity authorization relationship between the payload device and the flight platform. After binding, the aircraft allows the payload device to perform service interactions through the MQTT server. When unbound, the aircraft usually rejects all service requests.

**bind_required Event**

A device-level event actively pushed by the aircraft. When a device connects to the MQTT server and the aircraft detects that it is unbound, the aircraft pushes this event on the `thing/product/{client_id}/events` channel, carrying the current binding status (`bind_state`) and description information, prompting the payload to complete the binding process through DJI Assistant 2.

### Binding Status (BindState)

An enum describing the current binding progress of the device, with 9 values in total:

| Enum Constant | Value | Meaning |
|---|---|---|
| BIND_STATE_IDLE | 0 | Idle, binding check not yet started |
| BIND_STATE_CHECKING | 1 | Querying binding status |
| BIND_STATE_BOUND | 2 | Bound |
| BIND_STATE_BINDING | 3 | Binding, waiting for DJI Assistant 2 to complete binding |
| BIND_STATE_BIND_SUCCESS | 4 | Binding succeeded |
| BIND_STATE_BIND_FAILED | 5 | Binding failed |
| BIND_STATE_UNBINDING | 6 | Waiting for DJI Assistant 2 to complete unbinding |
| BIND_STATE_UNBIND_SUCCESS | 7 | Unbinding succeeded |
| BIND_STATE_UNBIND_FAILED | 8 | Unbinding failed |

### Monitoring Mechanism

The binding module registers a message listener on an existing MQTT session via `ThingModelClientSession_AddListener()`, without creating an additional MQTT connection. After the listener receives a message, it first verifies the message type and performs JSON decoding only when the message type is `bind_required`, to reduce the impact on the message dispatch process.

:::warning Warning:
The listener callback runs on the background message dispatch thread. Do not unregister the listener or destroy the session inside the callback, otherwise a deadlock will occur due to internal lock contention; nor should you call synchronous interfaces, otherwise the dispatch thread will be blocked until timeout, causing the response of this synchronous call to fail to be dispatched. Time-consuming logic should be handed off to other threads.
:::

## Feature Introduction

:::warning Warning:
The following code is for reference only and demonstrates the call flow and implementation of each feature. Developers can adapt it based on the hardware characteristics and application scenarios of the payload device.
:::

### Start Monitoring

Call `bind_monitor_start()` immediately after establishing the MQTT session to register the listener and subscribe to the event channel. This interface can be called repeatedly; repeated calls will not register the listener multiple times. For the corresponding MQTT protocol, see <a href="../api-reference/api-bind.html#bind-required-event" target="_blank" rel="noopener noreferrer">bind_required Event</a>.

```c
ThingModelClientSession_t *s = sample_session_open(&cfg);
if (!s) { /* Handle connection failure */ return -1; }

/* Register binding monitoring immediately after the session is established */
bind_monitor_start(s);
```

:::tip Note:
`bind_monitor_start()` internally calls `ThingModelClientSession_Subscribe()` to subscribe to `thing/product/{sn}/events`. When `auto_reconnect` is enabled, it automatically re-subscribes after reconnecting.
:::

### Query Binding Status

After starting monitoring, you can call the status query interfaces at any time in service code to decide whether to continue executing subsequent service requests.

```c
/* Conservative pass-through policy: treat as bound when no bind push has ever been received (the aircraft only pushes on exceptions; no push = no need to intercept) */
if (!bind_monitor_is_bound()) {
    printf("[main] Device is unbound, current bind_state=%d; please complete binding through DJI Assistant 2 and retry\n",
           bind_monitor_state());
    /* Wait for binding to complete before starting service features */
}

/* Strict determination: judge whether to pass through only after confirming a bind push has been received */
if (bind_monitor_got_push() && !bind_monitor_is_bound()) {
    printf("[main] Binding notification received, device is unbound (state=%d)\n", bind_monitor_state());
}
```

The following is the typical processing logic after the `bind_required` event is pushed:

```c
/* In the session listener callback (refer to the internal implementation of sample_bind.c) */
static void on_session_msg(void *user, const char *topic,
                           const char *payload, size_t len)
{
    /* Only handle messages from the event channel */
    if (!strstr(topic, "event"))                          return;
    /* Decode only when the target message is received */
    if (!payload_contains(payload, len, "bind_required")) return;

    T_BindRequired b;
    Bind_InitBindRequired(&b);
    if (BindJson_DecodeBindRequired(payload, &b) == THING_MODEL_RC_OK) {
        printf("[bind] Device binding status: %d (%s) — %s\n",
               (int)b.bind_state,
               b.bind_state_desc ? b.bind_state_desc : "-",
               b.message         ? b.message         : "-");
        if (b.bind_state != BIND_STATE_BOUND) {
            printf("[bind] Device is unbound/binding not completed, please complete binding through DJI Assistant 2 and retry\n");
        }
    }
    Bind_FreeBindRequired(&b);
}
```

Field descriptions of the event data structure `T_BindRequired`:

| Field | Type | Description |
|---|---|---|
| bind_state | E_BindState | Binding status enum, see [Binding Status (BindState)](#binding-status-bindstate) |
| bind_state_desc | char * | Status description string, such as "BINDING" |
| message | char * | Prompt information, such as "Binding in progress. Waiting for DA2 to complete binding." |
| timestamp_ms | int64_t | Timestamp when the aircraft sent it, in milliseconds |

### Stop Monitoring

When monitoring the binding status is no longer needed, call `bind_monitor_stop()` to unregister the listener and release resources.

```c
bind_monitor_stop();
sample_session_close(s);
```
