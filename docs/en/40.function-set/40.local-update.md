## Overview

Local Upgrade is used by the aircraft to upgrade the payload firmware online. The upgrade process is initiated by the aircraft: the aircraft sequentially issues four commands—enter upgrade mode, verify firmware, start upgrade, and finish upgrade—and the payload handles them as the responder.

The firmware file is transferred through the HTTP service on the payload, not via MQTT. During upgrade execution, the payload continuously reports the upgrade progress and result via MQTT.

:::tip Note:
- The C interfaces in PSDK encapsulate the underlying MQTT protocol. Developers can complete protocol interactions by calling the C interfaces directly, without manually constructing MQTT messages. For MQTT payload structures and field definitions, see <a href="../api-reference/api-local-update.html" target="_blank" rel="noopener noreferrer">Protocol Reference - Local Upgrade</a>.
- Before using this function, the payload device must first complete access and authentication. For details, see <a href="access-authentication.html" target="_blank" rel="noopener noreferrer">Access and Authentication</a>.
:::

## Basic Concepts

### Terminology

**Upgrade Command Responder**

The payload-side object used to receive and respond to the four upgrade commands issued by the aircraft. The payload registers a handler callback for each command, and the SDK invokes the corresponding callback when the aircraft issues the command.

**Upgrade Status Publisher**

The payload-side object used to actively report the upgrade status to the aircraft. During upgrade execution, the payload periodically pushes the current upgrade stage, progress, and final result through this object.

### Upgrade Sequence

The complete upgrade process is driven by the aircraft, and the payload responds in the following sequence:

1. **Enter Upgrade Mode**: The aircraft issues `enter_upgrade_mode`, and the payload returns the wait seconds `wait_time` and the firmware download address `url`.
2. **Verify Firmware**: After the aircraft downloads or uploads the firmware via `url`, it issues `check_firmware`, and the payload verifies the firmware and returns the result.
3. **Start Upgrade**: The aircraft issues `start_upgrade`, and the payload replies immediately, then performs the upgrade in the background and reports the upgrade progress and result through the publisher: upgrading (progress 0~100) → rebooting (reboot timeout seconds) → upgrade complete (success / failure). Among them, the upgrading and complete stages are pushed at 1 Hz.
4. **Finish Upgrade**: The aircraft issues `finish_upgrade`, and the payload stops the status push and replies.

:::warning Warning:
- After the payload receives `start_upgrade`, it should reply first, then start the background upgrade, to avoid blocking the command response.
- Once the upgrade starts, the payload process should keep running until `finish_upgrade` is received; exiting midway during the upgrade will cause the upgrade to fail.
- If the payload actually reboots during the upgrade, the upgrade result should be persisted before rebooting, and after rebooting the upgrade complete status should be pushed accordingly until `finish_upgrade` is received.
:::

## Feature Introduction

:::warning Warning:
The following code is for reference only and demonstrates the call flow and implementation of each feature. Developers can adapt it based on the hardware characteristics and application scenarios of the payload device.
:::

### Create Responder and Publisher

Create the upgrade command responder and status publisher on the established MQTT session `s`. Subsequent command callbacks are registered through the responder, and status pushes are sent through the publisher.

```c
UpgradeImpl_t *impl = UpgradeImpl_Create(s, device_sn);
Upgrade_Publisher_t *pub = Upgrade_CreatePublisher(s);
```

### Enter Upgrade Mode

Register the `Enter Upgrade Mode` callback. When the aircraft issues this command, the payload returns the seconds `wait_time` that the aircraft needs to wait and the firmware download address `url` in the callback. For the corresponding MQTT protocol, see <a href="../api-reference/api-local-update.html#enter-upgrade-mode" target="_blank" rel="noopener noreferrer">Enter Upgrade Mode</a>.

```c
static T_ThingModelReturnCode on_enter_mode(UpgradeImpl_t *impl, void *user,
                                            const T_Placeholder *req,
                                            T_UpgradeEnterModeReply *reply)
{
    reply->result         = 0;
    reply->result_message = strdup("ok");
    reply->wait_time      = 10;
    reply->url            = strdup("http://192.168.1.10:8000/upgrade.bin");
    return THING_MODEL_RC_OK;
}

UpgradeImpl_OnEnterUpgradeMode(impl, on_enter_mode, NULL);
```

:::tip Note:
The `result_message` and `url` of `T_UpgradeEnterModeReply` are `char *`, which the SDK releases after replying, so they must be heap-allocated via `strdup` or similar, and cannot use string literals or stack addresses.
:::

Field descriptions of the reply structure `T_UpgradeEnterModeReply`:

| Field | Type | Description |
|------|------|------|
| result | int32_t | Processing result, 0 indicates success |
| result_message | char * | Result description information |
| wait_time | int32_t | The seconds the aircraft should wait, used for the payload to prepare the storage area and other preliminary operations |
| url | char * | Firmware download address, from which the aircraft obtains the firmware via HTTP |

### Verify Firmware

Register the `Verify Firmware` callback. After the aircraft obtains the firmware, it issues this command, and the payload verifies the firmware and returns the result in the callback, setting `result` to a non-zero value when verification fails. For the corresponding MQTT protocol, see <a href="../api-reference/api-local-update.html#verify-firmware" target="_blank" rel="noopener noreferrer">Verify Firmware</a>.

```c
static T_ThingModelReturnCode on_check_firmware(UpgradeImpl_t *impl, void *user,
                                                const T_Placeholder *req,
                                                T_ThingModelCommonReply *reply)
{
    int ok = firmware_check();   /* Verify signature / decryption / integrity / version, return whether it passes */
    reply->result = ok ? 0 : -1;
    snprintf(reply->result_message, sizeof(reply->result_message),
             ok ? "firmware check ok" : "firmware invalid");
    return THING_MODEL_RC_OK;
}

UpgradeImpl_OnCheckFirmware(impl, on_check_firmware, NULL);
```

:::tip Note:
The `result_message` of `T_ThingModelCommonReply` is a fixed-length character array, which should be filled in with `snprintf` and should not use `strdup`.
:::

### Start Upgrade

Register the `Start Upgrade` callback. The payload replies immediately in the callback, then starts a background thread to perform the upgrade and push the upgrade progress and result, to avoid long-time blocking in the callback. For the corresponding MQTT protocol, see <a href="../api-reference/api-local-update.html#start-upgrade" target="_blank" rel="noopener noreferrer">Start Upgrade</a>.

```c
static T_ThingModelReturnCode on_start_upgrade(UpgradeImpl_t *impl, void *user,
                                               const T_Placeholder *req,
                                               T_ThingModelCommonReply *reply)
{
    reply->result = 0;
    snprintf(reply->result_message, sizeof(reply->result_message), "ok");
    start_upgrade_thread();   /* Perform the upgrade in the background and push the status through the publisher */
    return THING_MODEL_RC_OK;
}

UpgradeImpl_OnStartUpgrade(impl, on_start_upgrade, NULL);
```

### Finish Upgrade

Register the `Finish Upgrade` callback. The payload stops the status push and replies in the callback. For the corresponding MQTT protocol, see <a href="../api-reference/api-local-update.html#finish-upgrade" target="_blank" rel="noopener noreferrer">Finish Upgrade</a>.

```c
static T_ThingModelReturnCode on_finish_upgrade(UpgradeImpl_t *impl, void *user,
                                                const T_Placeholder *req,
                                                T_ThingModelCommonReply *reply)
{
    stop_upgrade_thread();     /* Stop the background upgrade and status push */
    reply->result = 0;
    snprintf(reply->result_message, sizeof(reply->result_message), "ok");
    return THING_MODEL_RC_OK;
}

UpgradeImpl_OnFinishUpgrade(impl, on_finish_upgrade, NULL);
```

### Upgrade State Push

During upgrade execution, the payload actively reports the upgrade status to the aircraft through the publisher, with stages in order: upgrading → rebooting (if a reboot is involved) → upgrade complete. The meaning of the `value` field changes with `upgrade_stage`. For the corresponding MQTT protocol, see <a href="../api-reference/api-local-update.html#upgrade-state-push" target="_blank" rel="noopener noreferrer">Upgrade State Push</a>.

```c
T_UpgradeStatePush p = { .upgrade_stage = UPGRADE_STAGE_UPGRADING, .value = 50 };
Upgrade_PublishPushUpgradeState(pub, &p);
```

Field descriptions of the push structure `T_UpgradeStatePush`:

| Field | Type | Description |
|------|------|------|
| upgrade_stage | E_UpgradeStage | Upgrade stage.<ul><li>UPGRADE_STAGE_IDLE (0): Idle</li><li>UPGRADE_STAGE_UPGRADING (3): Upgrading</li><li>UPGRADE_STAGE_COMPLETE (4): Upgrade complete</li><li>UPGRADE_STAGE_REBOOTING (6): Device rebooting</li></ul> |
| value | int32_t | The meaning changes with the stage.<ul><li>Upgrading: progress 0~100</li><li>Upgrade complete: result, 1 for success, 2 for failure</li><li>Device rebooting: reboot timeout seconds 0~255</li></ul> |

### Destroy Responder and Publisher

After the upgrade process ends, destroy the responder and publisher to release resources.

```c
UpgradeImpl_Destroy(impl);
Upgrade_DestroyPublisher(pub);
```
