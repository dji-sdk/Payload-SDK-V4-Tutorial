## Overview

The speaker widget is used by the payload to receive control commands and audio files delivered by the aircraft, and to periodically report its own status.

The aircraft can deliver work mode, play mode, volume settings, playback control, and audio transfer commands; the payload registers callbacks to respond to these commands and reports its current status via the publisher.

:::tip Note:
- The C interfaces in PSDK encapsulate the underlying MQTT protocol. Developers can complete protocol interactions by calling the C interfaces directly, without manually constructing MQTT messages. For MQTT payload structures and field definitions, see <a href="../api-reference/api-speaker.html" target="_blank" rel="noopener noreferrer">Protocol Reference - Speaker Widget</a>.
- Before using this feature, the payload device must first complete access and authentication. For details, see <a href="access-authentication.html" target="_blank" rel="noopener noreferrer">Access and Authentication</a>.
:::

## Basic Concepts

### Terminology

**Speaker Command Responder**

The payload-side object used to receive and respond to the eight speaker commands delivered by the aircraft. The payload registers a handler callback for each command, and the SDK invokes the corresponding callback when the aircraft delivers the command.

**Speaker Status Publisher**

The payload-side object used to proactively report speaker status to the aircraft. The payload periodically pushes the system state, work mode, play mode, volume, and current playback file information through this object.

**Work mode and play mode**

- Work mode `work_mode`: `0` is TTS (text-to-speech), `1` is voice (voice file).
- Play mode `play_mode`: `0` is single (single playback), `1` is loop (loop playback).

**Audio file chunked transfer**

When the aircraft transfers an audio file to the payload, it proceeds in three stages: "start → data packet → finish":
- `trans_start` declares the file metadata.
- `trans_data` transfers the audio data packet by packet (encoded as hex during transfer; the SDK automatically decodes it to binary).
- `trans_finish` carries the whole-file MD5 for the payload to verify.

### Audio Transfer Sequence

Audio file transfer must strictly follow the sequence below, and the payload-side callbacks are triggered in this order:

1. **trans_start**: The payload creates a temporary file, records the uuid and file name, and enters the transferring state (system_state=1).
2. **trans_data**: The payload writes the binary data of this packet into the temporary file according to `offset`; out-of-order delivery and retransmission are supported (located and overwritten by offset).
3. **trans_finish**: The payload closes the file, computes the MD5, and compares it with the `md5` in the request; if they match, it renames the file to the official file, otherwise it notifies the peer to retransmit.

:::warning Warning:
The `data` field in the `trans_data` request is a hex string during transfer, and the SDK has automatically decoded it to binary (`T_ThingModelBytes`); in the callback you can write it into the file according to `offset`. When the MD5 verification fails, return a non-zero result to notify the peer to retransmit; after retransmission exceeds the upper limit, terminate the transfer and clean up the session to avoid blocking the process for a long time.
:::

## Feature Introduction

:::warning Warning:
The following code is for reference only and demonstrates the call flow and implementation of each feature. Developers can adapt it based on the hardware characteristics and application scenarios of the payload device.
:::

### Create the Responder and the Publisher

On the established MQTT session `s`, create the speaker command responder and the status publisher. Subsequent command callbacks are registered through the responder, and status pushes are sent through the publisher.

```c
SpeakerImpl_t      *spimpl = SpeakerImpl_Create(s, device_sn);
Speaker_Publisher_t *sppub  = Speaker_CreatePublisher(s);
```

### Set Work Mode

Register the `Set Work Mode` callback. When the aircraft delivers this command, the payload updates the work mode (TTS / voice) in the callback and returns the result. For the corresponding MQTT protocol, see <a href="../api-reference/api-speaker.html#set-work-mode" target="_blank" rel="noopener noreferrer">Set Work Mode</a>.

```c
static T_ThingModelReturnCode on_set_work_mode(SpeakerImpl_t *impl, void *user,
        const T_SpeakerSetWorkModeRequest *req, T_ThingModelCommonReply *reply)
{
    AppSpeaker *app = user;
    app->work_mode = req->work_mode;
    reply->result = 0;
    snprintf(reply->result_message, sizeof(reply->result_message), "success");
    return THING_MODEL_RC_OK;
}

SpeakerImpl_OnSetWorkMode(spimpl, on_set_work_mode, &sp);
```

:::tip Note:
The `result_message` of `T_ThingModelCommonReply` is a fixed-length character array and should be filled in with `snprintf`, not `strdup`.
:::

Field description of the request structure `T_SpeakerSetWorkModeRequest`:

| Field | Type | Description |
|------|------|------|
| work_mode | int32_t | Work mode: 0 TTS (text-to-speech) / 1 voice (voice file) |

### Set Volume

Register the `Set Volume` callback. When the aircraft delivers this command, the payload verifies and updates the volume in the callback. For the corresponding MQTT protocol, see <a href="../api-reference/api-speaker.html#set-volume" target="_blank" rel="noopener noreferrer">Set Volume</a>.

```c
static T_ThingModelReturnCode on_set_volume(SpeakerImpl_t *impl, void *user,
        const T_SpeakerSetVolumeRequest *req, T_ThingModelCommonReply *reply)
{
    AppSpeaker *app = user;
    if (req->volume < 0 || req->volume > 100) {
        reply->result = -1;
        snprintf(reply->result_message, sizeof(reply->result_message), "volume out of range");
        return THING_MODEL_RC_OK;
    }
    app->play_volume = req->volume;
    reply->result = 0;
    snprintf(reply->result_message, sizeof(reply->result_message), "success");
    return THING_MODEL_RC_OK;
}

SpeakerImpl_OnSetVolume(spimpl, on_set_volume, &sp);
```

Field description of the request structure `T_SpeakerSetVolumeRequest`:

| Field | Type | Description |
|------|------|------|
| volume | int32_t | Volume, ranging from 0 to 100 |

### Start Audio Transfer

Register the `Start Audio Transfer` callback. When the aircraft starts transferring an audio file, it delivers this command, carrying the file type, uuid, file name, and decode bitrate. The payload creates a temporary file and enters the transferring state in the callback. For the corresponding MQTT protocol, see <a href="../api-reference/api-speaker.html#start-audio-transfer" target="_blank" rel="noopener noreferrer">Start Audio Transfer</a>.

```c
static T_ThingModelReturnCode on_trans_start(SpeakerImpl_t *impl, void *user,
        const T_SpeakerTransStartRequest *req, T_ThingModelCommonReply *reply)
{
    AppSpeaker *app = user;
    /* Create a temporary file by uuid, record file_name and uuid, and enter the transferring state */
    if (open_transfer_file(app, req->uuid, req->file_name) != 0) {
        reply->result = -1;
        snprintf(reply->result_message, sizeof(reply->result_message), "failed to create file");
        return THING_MODEL_RC_OK;
    }
    app->system_state = 1;   /* transmitting */
    reply->result = 0;
    snprintf(reply->result_message, sizeof(reply->result_message), "success");
    return THING_MODEL_RC_OK;
}

SpeakerImpl_OnTransStart(spimpl, on_trans_start, &sp);
```

Field description of the request structure `T_SpeakerTransStartRequest`:

| Field | Type | Description |
|------|------|------|
| file_type | int32_t | File type.<ul><li>0: tts_txt</li><li>1: opus</li><li>2: wav</li></ul> |
| uuid | char * | Unique identifier of this transfer |
| file_name | char * | Original file name |
| decode_bitrate | int32_t | Decode bitrate.<ul><li>8000</li><li>16000</li><li>24000</li><li>32000</li><li>48000</li><li>64000</li></ul> |

### Transfer Audio Data Packet

Register the `Transfer Audio Data Packet` callback. The aircraft delivers the audio binary data packet by packet, and the payload writes the data into the temporary file according to `offset`. For the corresponding MQTT protocol, see <a href="../api-reference/api-speaker.html#transfer-audio-data-packet" target="_blank" rel="noopener noreferrer">Transfer Audio Data Packet</a>.

```c
static T_ThingModelReturnCode on_trans_data(SpeakerImpl_t *impl, void *user,
        const T_SpeakerTransDataRequest *req, T_ThingModelCommonReply *reply)
{
    AppSpeaker *app = user;
    /* req->data has already been decoded from hex to binary by the SDK (T_ThingModelBytes) */
    if (req->data.data && req->data.len > 0) {
        fseek(app->xfer.fp, req->offset, SEEK_SET);
        fwrite(req->data.data, 1, req->data.len, app->xfer.fp);
    }
    reply->result = 0;
    snprintf(reply->result_message, sizeof(reply->result_message), "success");
    return THING_MODEL_RC_OK;
}

SpeakerImpl_OnTransData(spimpl, on_trans_data, &sp);
```

:::warning Warning:
The `data` field of `T_SpeakerTransDataRequest` is of type `T_ThingModelBytes` (containing a `data` pointer and a `len` length). The SDK has already decoded it from a hex string to binary, so in the callback you can write it according to `offset` without further hex decoding.
:::

Field description of the request structure `T_SpeakerTransDataRequest`:

| Field | Type | Description |
|------|------|------|
| packet_index | int32_t | Packet index |
| offset | int32_t | Byte offset of this packet in the file |
| data | T_ThingModelBytes | Audio binary data of this packet (containing a data pointer and a len length) |

### Finish Audio Transfer

Register the `Finish Audio Transfer` callback. After the aircraft completes the transfer, it delivers this command, carrying the whole-file MD5. The payload computes the file MD5 in the callback and compares it with the request value; if they match, it saves the file as the official file, otherwise it notifies the peer to retransmit. For the corresponding MQTT protocol, see <a href="../api-reference/api-speaker.html#finish-audio-transfer" target="_blank" rel="noopener noreferrer">Finish Audio Transfer</a>.

```c
static T_ThingModelReturnCode on_trans_finish(SpeakerImpl_t *impl, void *user,
        const T_SpeakerTransFinishRequest *req, T_ThingModelCommonReply *reply)
{
    AppSpeaker *app = user;
    char got[33] = "";
    close_and_md5(app, got);   /* Close the file and compute the MD5 */

    if (req->md5 && strcasecmp(got, req->md5) != 0) {
        reply->result = -1;
        snprintf(reply->result_message, sizeof(reply->result_message), "md5 mismatch");
        return THING_MODEL_RC_OK;   /* Return failure to notify the peer to retransmit */
    }
    commit_transfer_file(app);      /* Verification passed; rename to the official file */
    app->system_state = 0;          /* idle */
    reply->result = 0;
    snprintf(reply->result_message, sizeof(reply->result_message), "success");
    return THING_MODEL_RC_OK;
}

SpeakerImpl_OnTransFinish(spimpl, on_trans_finish, &sp);
```

Field description of the request structure `T_SpeakerTransFinishRequest`:

| Field | Type | Description |
|------|------|------|
| md5 | char * | Whole-file MD5 (32-character hex), used to verify transfer integrity |

### Speaker State Push

Proactively report the current speaker status to the aircraft through the publisher. After constructing the status structure, call the push interface. For the corresponding MQTT protocol, see <a href="../api-reference/api-speaker.html#speaker-state-push" target="_blank" rel="noopener noreferrer">Speaker State Push</a>.

```c
T_SpeakerStatePush push = {
    .system_state   = 2,       /* playing */
    .work_mode      = 1,       /* voice */
    .play_mode      = 0,       /* single */
    .play_volume    = 50,
    .play_file_name = (char *)"alarm.opus",
    .play_file_uuid = (char *)"1a2b3c4d",
};
Speaker_PublishState(sppub, &push);
```

Field description of the push structure `T_SpeakerStatePush`:

| Field | Type | Description |
|------|------|------|
| system_state | int32_t | System state.<ul><li>0: idle</li><li>1: transmitting</li><li>2: playing</li><li>3: error</li><li>4: tts_conversion</li></ul> |
| work_mode | int32_t | Work mode.<ul><li>0: TTS</li><li>1: voice</li></ul> |
| play_mode | int32_t | Play mode.<ul><li>0: single</li><li>1: loop</li></ul> |
| play_volume | int32_t | Current volume, 0~100 |
| play_file_name | char * | Current playing file name |
| play_file_uuid | char * | Current playing file uuid |

### Destroy the Responder and the Publisher

When the speaker feature is no longer used, destroy the responder and the publisher to release resources.

```c
Speaker_DestroyPublisher(sppub);
SpeakerImpl_Destroy(spimpl);
```
