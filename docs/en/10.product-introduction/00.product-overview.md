

## Overview

Payload SDK is a set of software development interfaces for extending the payload capabilities of aircraft. It supports developers in integrating self-developed or third-party payloads into the DJI aircraft platform to achieve remote control, data interaction, and system collaboration. The SDK uses the open MQTT protocol as its communication foundation, and all sample code is provided in source form. To develop safe and reliable payload devices with Payload SDK, keep track of release information and upgrade to the <a href="../" target="_blank" rel="noopener noreferrer">latest development package</a> in a timely manner.

## Terminology

| Term | Meaning |
|---|---|
| MQTT communication protocol | The MQTT-based application-layer communication protocol between the aircraft payload and the platform, which defines four types of interactions: service, property, event, and state |
| MQTT Broker | The MQTT server that carries the communication protocol, responsible for device access, message routing, and remote management; hereinafter referred to as the Broker |
| Payload device | A functional device developed with this SDK that can be mounted on an aircraft, such as a speaker, searchlight, or detector |
| Onboard computing platform | The computing unit mounted on the aircraft, which can serve as the runtime carrier for payload business and the SDK |
| Platform-side application | The cloud service or mobile App of the platform, used to send commands to payload devices and subscribe to data |

## System Roles and Usage

In practical applications, an aircraft system is usually composed of a flight platform, payload devices, an onboard computing platform, and platform-side applications working together. As the core interface for payload capability access and extension, this SDK is responsible for the communication, control, and data interaction between the payload and the platform. It resides on the device side and serves as the protocol access layer between the payload and the platform.

After integrating the SDK, the payload device connects to the Broker over MQTT and interacts with the platform according to the communication protocol: the SDK parses commands sent by the platform into calls the device can handle, and reports the device's execution results, status, and events according to the protocol. In this way, the device side only needs to focus on function implementation, while communication, authentication, and reconnection are all handled by the SDK.

Depending on the runtime location, the SDK supports two deployment forms:

- **Running on the payload itself**: The SDK is integrated directly on the payload device's embedded controller (such as MCU / RTOS) to implement the payload's own functions;
- **Running on the onboard computing platform**: The SDK is integrated on the onboard computing platform (such as Linux) to collaborate with the payload device and the platform, suitable for scenarios with high computing power requirements.

## Access Methods

Payload access is divided into four stages:

1. **Apply for credentials**: Obtain enterprise-level App credentials (App ID / Key / License) and the device identity (Device SN).
2. **Define capabilities**: Declare the services, properties, events, and states that the payload provides externally.
3. **Integrate and implement**: Integrate the SDK into the payload firmware or the onboard computing platform and implement the declared capabilities.
4. **Come online and run**: The device automatically comes online after connecting to the network and completing authentication, and accepts platform management.

After the device comes online, it provides capabilities externally through four types of protocol interactions:

| Interaction Type | Semantics | Direction |
|---|---|---|
| Service | Execute a one-time action and return a result | Bidirectional: the payload or the aircraft initiates the request, and the other party executes it and returns a receipt |
| Property | Read or set device configuration items | Bidirectional: the payload or the aircraft initiates the read/write, and the other party responds |
| Event | Occasional event notifications | Bidirectional: the payload or the aircraft pushes on demand |
| State | Periodic or changed states of the payload | Reported by the payload to the aircraft |
| OSD | Periodic or changed states of the aircraft | Pushed by the aircraft to the payload |

The initiator and the send/receive direction of each specific interface are subject to the protocol definition of the corresponding feature. For details, see <a href="../api-reference/api-bind.html">Protocol Reference</a>.

In addition to the above interactions, the SDK supports remote OTA firmware upgrades, as well as data pass-through and subscription between the payload and the aircraft, and between the payload and the cloud.

## Key Advantages

**Fully open protocol and source code**  
The communication process is auditable and the interfaces are verifiable, with no binary black box, facilitating security assessment and independent customization.

**Unified payload access capability**  
Payload capabilities are declared and integrated using a unified interface specification, reducing the access cost of different payload types. The access process is standardized and consistent, reducing the joint-debugging work of protocol integration.

**Support for multiple deployment forms**  
It can run on the payload itself (MCU / RTOS) or on the onboard computing platform (Linux), meeting different computing power requirements and system architecture choices.

**Comprehensive functional coverage**  
It provides basic capabilities such as information acquisition, data transmission, and power management, as well as functions such as widget interaction, remote upgrade, data pass-through and subscription, and time synchronization. Developers can combine them into full-featured payload devices according to industry needs, and easily integrate third-party sensors and detection devices to collect required data.

**Broad software and hardware platform compatibility**  
It can run on mainstream embedded MCUs and operating systems, covering a variety of runtime environments from bare metal and RTOS to Linux. The transport, encryption, and system adaptation layers are all replaceable, and the SDK can run on different software and hardware platforms by following the cross-platform porting steps.

**Secure and reliable connection**  
Built-in TLS encryption and two-phase identity authentication; supports automatic reconnection and subscription recovery after disconnection, ensuring that the device remains continuously controllable and subscriptions are not lost in weak network environments.

## Supported Payload Capabilities

| Capability | Description | Typical Scenario |
|---|---|---|
| Binding status notification | Monitor and query the payload's binding status on the platform side | Payload authorization verification, unbound interception |
| Aircraft information | Report information such as aircraft model, firmware version, and onboard device inventory | Payload identification, health information, extended interaction |
| Data subscription | Subscribe to/unsubscribe from telemetry topics, query the latest values | Real-time telemetry monitoring, data dashboards |
| Local upgrade | The platform/aircraft side sends OTA upgrades to the payload | Remote payload maintenance, batch firmware updates |
| Custom widget | Present custom widgets on the App/remote controller, supporting reading and writing of widget values | Custom control panels for payloads such as searchlights and droppers |
| Speaker | Work/play mode and volume settings, playback control, audio chunked transmission | Emergency broadcasting, warning and deterrence, publicity broadcasting |
| GEO Caging | The payload triggers the flight platform to stop propellers via a hardware PWM signal | Emergency flight termination, safety protection |
| Time synchronization | Synchronize device time with system time (including PPS) | Multi-sensor time alignment, precise surveying and mapping |
| Data transmission | A data pipeline between the payload and the aircraft | Custom protocols, private data return |
| Power management | Actions and states related to payload power supply | Payload energy management, power supply protection |
| SDK interconnection | Data interaction between the payload and other SDK devices (MOP channel) | Multi-SDK collaboration, private data links |
