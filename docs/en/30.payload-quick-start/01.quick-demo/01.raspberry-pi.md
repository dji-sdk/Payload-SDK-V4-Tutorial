

## Introduction
This article uses a quick-start demo based on the **Raspberry Pi 4B development board** to guide developers through the complete process—from hardware connection, PSDK environment preparation, and sample program configuration to demo running and validation—in the shortest possible time.

:::tip Note:
Minimum version requirement: no lower than PSDK V4.0.0
:::

## What You Will Achieve with This Demo
After completing this quick-start demo, you will be able to:
- Use a **Raspberry Pi 4B** as an external Linux payload device.  
- Connect the Raspberry Pi development board to the Matrice 5TD flight platform via the **E-Port V3 development board**.  

## Basic Knowledge Overview

The following is an introduction to the hardware devices required for this tutorial. It is recommended that you review the related materials before proceeding with the subsequent sections.
* [Raspberry Pi 4B Developer Kit](https://www.raspberrypi.com/products/raspberry-pi-4-model-b/)
* E‑Port V3 Developer Kit


## Hardware Environment Setup
### Device Connection

#### Matrice 5TD Device Connection
##### Connecting the Device via the E-Port V3 Port

All E-Port V3 ports on the Matrice 5TD support connecting payload devices. E1 is the high-speed port (supports USB 3.0), while E2/E3 are low-speed ports (support USB 2.0). The figure below uses the E3 low-speed port as an example. For high-speed data capabilities, use the E1 high-speed port. For details, see <a href="../configure-the-hardware-environment/drone-port.html#e-port-v3-port" target="_blank" rel="noopener noreferrer">E-Port V3 Port</a>.

1. Set the port toggle switch on the E-Port V3 development board to the "E-PORT V3" side.
2. Set the ENABLE switch on the E-Port V3 development board to "ON", and set the SWITCH to the "EXPAND" side.
3. Use an E-Port V3 coaxial cable to connect the E-Port V3 development board to the E-Port V3 port on the Matrice 5TD aircraft body.
4. After flashing the official system image onto the Raspberry Pi 4B development board, use a USB cable to connect the USB port of the E-Port V3 development board to the power port of the Raspberry Pi 4B development board (which includes USB 2.0 communication capability).
5. Power on the entire aircraft, and check whether the green power indicator on the E-Port V3 development board is lit and whether the Raspberry Pi has started normally.

## Software Environment Setup
### Installing the Software Environment
1. The Raspberry Pi 4B development kit does not include an SD card or the Raspberry Pi OS 64-bit system image by default. Please refer to the [Raspberry Pi flashing guide](https://shumeipai.nxez.com/2013/09/07/how-to-install-and-activate-raspberry-pi.html) to flash the image and configure the account.
2. After completing the [Hardware Environment Setup](#hardware-environment-setup) and finishing startup, enter the configured account and password, and check whether you can log in to the Raspberry Pi desktop system.
3. After entering the desktop, you can visit a web page through the browser to check whether the network environment of the Raspberry Pi 4B is working properly.
4. Before running PSDK, you need to install dependency libraries such as OpenSSL, Mosquitto, cJSON, and Mongoose. Please refer to the shell commands below to complete the installation and check whether the installation is successful.

#### Installing Runtime Dependencies on the Target Raspberry Pi
On the Raspberry Pi, the sample program requires the following dynamic libraries (OpenSSL, Mosquitto, cJSON) at startup:

```bash
sudo apt-get update
sudo apt-get install -y libssl3 libmosquitto1 libcjson1
```

If `libmosquitto.so.1` / `libssl.so.3` is reported as missing during subsequent running, install the corresponding version according to the actual package name.

#### Installing Build Dependencies on the Compilation Host
On the host (PC) used for cross-compilation, you need to install the toolchain and header file dependencies:

```bash
sudo apt-get update
sudo apt-get install -y build-essential cmake python3 zip git
sudo apt-get install -y gcc-aarch64-linux-gnu
sudo apt-get install -y libssl-dev libmosquitto-dev libcjson-dev
```

> Note: Cross-compilation links against the dynamic libraries of the target architecture (aarch64), but the CMake build still requires the OpenSSL / mosquitto header files on the host. `libmongoose-dev` does not have a system package in most distributions; if you compile the widget sample, you need to manually provide the mongoose source code. If the HTTP file service of widget/upgrade is not enabled, you can skip it. For the complete toolchain version requirements, see <a href="../config-develop-environment.html#configure-the-linux-development-environment" target="_blank" rel="noopener noreferrer">Configure Development Environment - Configure the Linux Development Environment</a>.


### Enabling the USB Device Function of the Raspberry Pi 4B

You can refer to the [Raspberry Pi bulk endpoint configuration guide](https://sdk-forum.dji.net/hc/zh-cn/articles/10232604141465-M30%E5%BC%80%E5%8F%91-%E6%A0%91%E8%8E%93%E6%B4%BE4B%E9%85%8D%E7%BD%AEUSB-device-RNDIS-%E5%92%8C-BULK) to enable the USB device function of the Raspberry Pi 4B.
:::tip Note:
You need to replace `raspi-usb-device-start.sh` with the following content.
- Set the VID:PID to 2CA3:F004.<br>
:::

```shell
#!/bin/bash

# The IP address shared by all USB network interfaces created by this script.
net_ip=192.168.42.120
# The associated netmask.
net_mask=255.255.0.0

enable_vcom=0
enable_rndis=0
enable_bulk=1

startup_bulk_dir=$(dirname "$0")
startup_bulk_exe=${startup_bulk_dir}/build/startup_bulk

if [ ! -d /sys/kernel/config/usb_gadget ]; then
    if ! $(grep -q dtoverlay=dwc2 /boot/config.txt) ; then
        echo -e "\n\n\n## customized\n# for op-sdk enable USB device RNDIS\n[all]\ndtoverlay=dwc2" >> /boot/config.txt
        init 6
    fi

    if ! $(grep -q modules-load=dwc2 /boot/cmdline.txt) ; then
        sed -i 's/rootwait /&modules-load=dwc2 /' /boot/cmdline.txt
        init 6
    fi

    if ! $(grep -q libcomposite /etc/modules) ; then
        echo -e "\n\n\n## customized\n# for op-sdk enable USB device RNDIS\nlibcomposite" >> /etc/modules
        init 6
    fi

    exit 1
fi

modprobe g_ether
rmmod g_ether
sleep 1

if [ ! -d /sys/kernel/config/usb_gadget/pi4 ]; then
    mkdir -p /sys/kernel/config/usb_gadget/pi4
    cd /sys/kernel/config/usb_gadget/pi4
        echo 0x2ca3 > idVendor # DJI
        echo 0xF004 > idProduct # Multifunction Composite Gadget

        if [ ${enable_vcom} -eq 1 ]; then
            echo 0xF004 > idProduct # Multifunction Composite Gadget
        fi

        if [ ${enable_rndis} -eq 1 ]; then
            echo 0xF004 > idProduct # Multifunction Composite Gadget
        fi

        if [ ${enable_bulk} -eq 1 ]; then
            echo 0xF004 > idProduct # Multifunction Composite Gadget
        fi

        echo 0x0001 > bcdDevice # v1.0.0
        echo 0x0200 > bcdUSB # USB2

        echo 0xEF > bDeviceClass
        echo 0x02 > bDeviceSubClass
        echo 0x01 > bDeviceProtocol

        mkdir -p strings/0x409
            echo "psdk-rpi4b" > strings/0x409/serialnumber
            echo "raspberry" > strings/0x409/manufacturer
            echo "PI4" > strings/0x409/product

        cfg=configs/c.1

        mkdir -p "${cfg}"
            echo 0x80 > ${cfg}/bmAttributes
            echo 250 > ${cfg}/MaxPower

        cfg_str=""

        if [ ${enable_rndis} -eq 1 ]; then
            cfg_str="${cfg_str}+RNDIS"
            func=functions/rndis.usb0
            mkdir -p "${func}"
                ln -sf "${func}" "${cfg}"

            # Informs Windows that this device is compatible with the built-in RNDIS
            # driver. This allows automatic driver installation without any need for
            # a .inf file or manual driver selection.
            echo 1 > os_desc/use
            echo 0xcd > os_desc/b_vendor_code
            echo MSFT100 > os_desc/qw_sign
                echo RNDIS > "${func}/os_desc/interface.rndis/compatible_id"
                echo 5162001 > "${func}/os_desc/interface.rndis/sub_compatible_id"

            ln -sf "${cfg}" os_desc
        fi

        if [ ${enable_vcom} -eq 1 ]; then
            cfg_str="${cfg_str}+ACM0"
            func=functions/acm.gs0
            mkdir -p "${func}"
            ln -sf "${func}" "${cfg}"
        fi

        if [ ${enable_bulk} -eq 1 ]; then
            mkdir -p /dev/usb-ffs

            cfg_str="${cfg_str}+BULK1"
            mkdir -p /dev/usb-ffs/bulk1
            func=functions/ffs.bulk1
            mkdir -p "${func}"
            ln -sf "${func}" "${cfg}"
            mount -o mode=0777,uid=2000,gid=2000 -t functionfs bulk1 /dev/usb-ffs/bulk1

            cfg_str="${cfg_str}+BULK2"
            mkdir -p /dev/usb-ffs/bulk2
            func=functions/ffs.bulk2
            mkdir -p "${func}"
            ln -sf "${func}" "${cfg}"
            mount -o mode=0777,uid=2000,gid=2000 -t functionfs bulk2 /dev/usb-ffs/bulk2

            cfg_str="${cfg_str}+BULK3"
            mkdir -p /dev/usb-ffs/bulk3
            func=functions/ffs.bulk3
            mkdir -p "${func}"
            ln -sf "${func}" "${cfg}"
            mount -o mode=0777,uid=2000,gid=2000 -t functionfs bulk3 /dev/usb-ffs/bulk3
        fi

        mkdir -p "${cfg}/strings/0x409"
        echo "${cfg_str:1}" > "${cfg}/strings/0x409/configuration"
    # cd -

fi

if [ ${enable_bulk} -eq 1 ]; then
    if [ ! -f ${startup_bulk_exe} ]; then
        cd ${startup_bulk_dir}
            make && ( $? != 0 ) && ( exit 1 )
            cp startup_bulk ${startup_bulk_exe}
            make clean
        cd -
    fi

    ${startup_bulk_exe} /dev/usb-ffs/bulk1 &
    sleep 1
    ${startup_bulk_exe} /dev/usb-ffs/bulk2 &
    sleep 1
    ${startup_bulk_exe} /dev/usb-ffs/bulk3 &
    sleep 1
fi

    udevadm settle -t 5 || :
    ls /sys/class/udc > UDC

if [ ${enable_rndis} -eq 1 ]; then
    /sbin/brctl addbr pi4br0
    /sbin/ifconfig pi4br0 ${net_ip} netmask ${net_mask} up

    /sbin/brctl addif pi4br0 usb0
    /sbin/ifconfig usb0 down
    /sbin/ifconfig usb0 up
fi
exit 0

```

git clone https://github.com/dji-sdk/Payload-SDK-V4.git

### Fill In the Application Information

Fill in the information obtained in the previous step <a href="#obtaining-application-information">Obtaining Application Information</a> into the local configuration:

```bash
cd projects/linux
cp sample_config_local.h.example sample_config_local.h
# Edit sample_config_local.h and fill in the real App ID, App Key, App License, Broker address, and CA certificate path
```

Description of the configuration items (at runtime, you can also override them with the environment variables of the same name `THING_MODEL_*`):

| Configuration Item | Type | Required | Meaning and How to Fill In |
|:---|:---|:---|:---|
| SAMPLE_DEFAULT_APP_ID | string | Yes | Application ID. Fill in the string assigned by the platform. |
| SAMPLE_DEFAULT_APP_NAME | string | No | Application name, i.e., the name entered when creating the application (such as `psdkappfortest`). The server uses it to identify the application; filling it in is recommended. |
| SAMPLE_DEFAULT_APP_KEY | string | Yes | Application key. Keep it safe and do not hard-code it into the repository. |
| SAMPLE_DEFAULT_APP_LICENSE | string | Yes | Application license. |
| SAMPLE_DEFAULT_DEVICE_SN | string | Yes | Serial number of the payload device, customized by the payload developer (**not the aircraft SN**). It identifies the connected payload and also serves as the MQTT connection identifier and the `{client_id}` in each business Topic.<br>Format: digits, letters, and underscores (`_`), no more than 64 characters. Ensure that each payload device uses a unique SN. |
| SAMPLE_DEFAULT_BROKER | string | Yes | Address of the broker on the aircraft side. Fill it in according to the aircraft model; for example, it is `192.168.100.3` for the Matrice 5TD. |
| SAMPLE_DEFAULT_CA_CERT | string | Yes | Path of the CA certificate (`ca.crt`), used to verify the broker's server certificate. For how to obtain the certificate, see <a href="#download-the-certificate">Download the Certificate</a>. |

### Build the Sample

The Payload SDK sample merges all feature samples into a single `sample_things_model` executable, which can be selected and run through a menu or command-line arguments.

The Raspberry Pi 4B is an aarch64 target platform, so you need to perform **AArch64 cross-compilation** on the compilation host (PC) and then copy the artifacts to the Raspberry Pi to run:

```bash
cmake -B build_aarch64 -S projects/linux -DSAMPLE_BUILD=cross
cmake --build build_aarch64 -j
```

After the build is complete, confirm that the artifact is arm64:

```bash
file build_aarch64/sample_things_model
# ELF 64-bit LSB shared object, ARM aarch64, version 1 (SYSV), dynamically linked, ...
```

### Configure the Network Connection

The payload program needs to communicate through the aircraft-side broker, so before running it you must first connect the Raspberry Pi to the aircraft's network. The Raspberry Pi is connected to the aircraft via a USB network (network interface `usb0`), and its IP is assigned by the aircraft via DHCP. Since different payload ports are assigned different subnets, the IP must be read dynamically on the device and should not be hard-coded.

:::tip Note:
`usb0` belongs to the bridge `pi4br0`, and the actual network communication is handled by `pi4br0`. Therefore, you need to configure the IP and route assigned by the aircraft onto `pi4br0`, while keeping `usb0` unchanged. All the following steps require root privileges (`sudo`), and only need to be executed once after each system startup.
:::

#### 1. Obtain the IP and Gateway

Trigger DHCP on `usb0` to request an IP from the aircraft:

```text
sudo dhclient -v usb0        # A DHCPACK in the output indicates a successful request
```

After a successful request, read the IP (including the mask) and gateway assigned by the aircraft for use in subsequent steps.

Read the IP and mask:

```text
ip -4 -o addr show dev usb0
```

The output is similar to `inet 192.168.150.2/24 ...`, where `192.168.150.2` is the IP and `/24` is the mask.

Read the gateway (the address after `via` in the default route):

```text
ip -4 -o route show default dev usb0
```

The output is similar to `default via 192.168.150.1 dev usb0 proto dhcp src 192.168.150.2 ...`, where `192.168.150.1` is the gateway.

In the example above, the IP is `192.168.150.2/24` and the gateway is `192.168.150.1`; the actual values depend on what is read from the device.

#### 2. Configure the IP onto the Bridge

Remove the IP on `usb0` and configure it onto `pi4br0`:

```text
sudo ip addr del 192.168.150.2/24 dev usb0
sudo ip addr add 192.168.150.2/24 dev pi4br0
```

#### 3. Configure the Route

Configure a route to the broker subnet so that the Raspberry Pi can access the broker. Taking the Matrice 5TD as an example (broker subnet `192.168.100.0/24`, broker address `192.168.100.3`), please replace it according to the aircraft model you use.

There may be multiple IPs on `pi4br0`, so you need to use `src` to specify the IP of the aircraft subnet as the source address:

```text
sudo ip route add 192.168.100.0/24 via 192.168.150.1 dev pi4br0 src 192.168.150.2
```

#### 4. Verify Connectivity

Execute the following command. If you can ping the broker address, it means the network is ready and you can continue to run the payload program:

```text
ping -c 3 192.168.100.3
```


### Run the Sample

The cross-compilation artifacts need to be copied to the Raspberry Pi to run:

```bash
cd build_aarch64

# Interactive menu: lists all samples, enter the number to select, q to quit; during running press Ctrl-C to stop the current sample and return to the menu
./sample_things_model

# Directly run a specific sample (arguments are passed through to the sample)
./sample_things_model data_subscription --verbose
./sample_things_model widget --debug
./sample_things_model time_sync --gpio 26

# List samples / general help / a sample's own arguments
./sample_things_model --list
./sample_things_model --help
./sample_things_model data_subscription -h
```

For the first access verification, it is recommended to run `data_subscription` first. It only subscribes to FC telemetry data and queries the latest value, and does not issue any control commands.


### Environment Variable Override

At runtime, you can override `sample_config_local.h` or the source-code default values:

```bash
export THING_MODEL_BROKER=ssl://your-broker:8883
export THING_MODEL_APP_ID=...

```

## Application Binding

After the payload device accesses the MQTT broker, it must first complete **application binding** before the aircraft will allow business requests. When the device is not bound, the aircraft pushes a `bind_required` notification on the event channel and refuses to handle business features such as the speaker and custom widget. For the binding concept and process, see <a href="../app-bind.html" target="_blank" rel="noopener noreferrer">Application Binding</a>.

Before running the demo, please confirm:

1. The payload device has successfully accessed the broker through authentication.
2. Device binding has been completed via DJI Assistant 2.
3. The demo program monitors the binding status, and only starts the business features after confirming that `bind_state` is bound.

For the usage of the interfaces for monitoring and querying the binding status, see <a href="../../function-set/bind.html" target="_blank" rel="noopener noreferrer">Function Set - Binding Status Notification</a>.
