## Introduction

This article uses a quick-start demo based on the **E‑Port V3 development kit** to help developers complete the entire process—from payload hardware integration and PSDK sample configuration to demo running and validation—in the shortest possible time.  
Through this demo, developers can quickly understand the **PSDK-based payload development approach** and learn how a payload device establishes communication and interaction with the flight platform and DJI Pilot via the E‑Port V3 port.

## What You Will Achieve with This Demo
After completing this quick-start demo, you will be able to:
- Use the E‑Port V3 development board as a payload device and connect it to the flight platform via hardware.  
- Run the PSDK sample program on the GD32F527 onboard MCU.  
- Successfully run the payload demo program and establish communication with the flight platform.  
- Verify on DJI Pilot that the payload is correctly recognized, and complete basic interaction validation.  

## E‑Port V3 Development Kit Overview
The E-Port V3 development kit makes it convenient for developers to quickly start PSDK payload development based on the E-Port V3 port, ready to use out of the box. It can convert the E-Port V3 port into common communication ports and power ports, facilitating development and debugging.  
The E-Port V3 development board has a built-in MCU, model GD32F527ZMT7, with 8 MB of external SDRAM. Its device specifications and technical documentation can be obtained from the GD32 official website.  
The E-Port V3 development board is also compatible with the E-Port V2 port, and you can select the E-Port V2 or E-Port V3 port mode via the toggle switch on the development board.  
Through the switch (labeled 11 in the figure), you can switch to connect to an external device; the external device needs to be connected to the USB port (labeled 12 in the figure), and this USB can be connected to the USB Device port of a third-party MCU or SoC development board. 
:::tip Note:
Minimum version requirement: no lower than PSDK V4.0.0
:::

* Power switch (labeled ENABLE): Controls the aircraft power input by toggling ON or OFF; next to the switch is a green power indicator.
* Reset button: The button labeled RESET in the lower right corner, used to reset the MCU.
* Programming port: The pins labeled SDIO next to the reset button in the lower right corner, supporting programming the MCU chip via the SWD port.
* Debug serial port: The four pins labeled Debug in the lower right corner, where TX/RX correspond to the PA0/PA1 pins of the MCU respectively.
* Power output: 3 XT30 ports, providing power output with voltages of 5V/12V/VCC respectively.
* Onboard Authentication Chip Enable Switch: The silkscreen is JM and is used to select the authentication chip source. By default, it is set to N, which uses the authentication chip built into the E-Port V3 coaxial cable. When set to Y, the onboard authentication chip on the development board is used, which is applicable when making or verifying a custom cable.
* Loader button: Labeled Loader in the lower left corner; it can force the MCU into the Loader for upgrade during reset (the matching Loader firmware needs to be flashed).
* SWITCH switch: The USB signal selection switch. When the switch is set to ONBOARD, the USB 2.0 signal of the E-Port port is connected to the MCU, and it can be used as a development board to develop PSDK devices; when the switch is set to the EXPAND side, the USB 2.0/3.0 signal of the E-Port port can be connected to the Type-A port, and it can be used as an adapter board to access external PSDK devices for secondary development.
* USB port: The aircraft acts as the Host, and the USB of the onboard MCU / external expansion device acts as the Device.
* Expansion IO: There is a row of expansion IO next to the debug serial port. The pin definitions are as follows, and can be used flexibly according to the actual situation.

### Matrice 5TD Device Connection

All E-Port V3 ports on the Matrice 5TD support connecting payload devices. E1 is the high-speed port (supports USB 3.0), while E2/E3 are low-speed ports (support USB 2.0). The figure below uses the E3 low-speed port as an example. For high-speed data capabilities, use the E1 high-speed port. For details, see <a href="../configure-the-hardware-environment/drone-port.html#e-port-v3-port" target="_blank" rel="noopener noreferrer">E-Port V3 Port</a>.  
Before connecting, set the port toggle switch on the development board to **E-Port V3** mode. Use an E-Port V3 coaxial cable to connect the E‑Port V3 development board to the E‑Port V3 port on the Matrice 5TD.

## Download the Certificate

Go to the <a href="https://developer.dji.com/cn/payload-sdk/downloads/" target="_blank" rel="noopener noreferrer">Developer Center download page</a>, click "DOWNLOAD" at **Payload Certificate**, and obtain the TLS CA certificate (`ca.crt`). This certificate is used to verify the identity of the MQTT broker server. The RTOS sample project already embeds this certificate in `projects/rtos/gd32f527/network/tls/ca_cert.h` and can be used directly; your own project can embed the CA as a C array in the same way, referring to `projects/rtos/gd32f527/app/ca_cert_provider.c`.

## Run the Demo

Before starting, first follow <a href="../config-develop-environment.html" target="_blank" rel="noopener noreferrer">Configure Development Environment</a> to complete the installation of the RTOS toolchain (Keil MDK, GD32F527 driver package). If you want to further understand how the SDK-side code calls the payload capabilities, refer to <a href="../getting-started-with-psdk.html" target="_blank" rel="noopener noreferrer">Getting Started with PSDK</a>.

Obtain the PSDK source code:

```bash
git clone https://github.com/dji-sdk/Payload-SDK-V4.git
cd Payload-SDK-V4
```

When using the E-Port V3 development board (with an MCU such as GD32F527), you need to integrate the sample into your RTOS/bare-metal project. The core steps are:

1. **Organize the source code**: Add `samples/launcher/`, the required sample's `samples/<cap>/src/*.c`, the protocol code under `sdk/generated/c/`, and `sdk/runtime/c/src/` (excluding the POSIX/mosquitto desktop implementation) to the project.
2. **Implement the platform glue**:
   - Implement `T_ThingModelOsal` (threads, locks, events, delays);
   - Implement the MQTT transport vtable and the HMAC-SHA256 crypto vtable (or use an existing library on the platform);
   - Redirect `printf` to UART.
3. **Fill in the application information**: Fill in the information obtained in the previous step <a href="#obtaining-application-information">Obtaining Application Information</a> into `projects/rtos/gd32f527/app/sample_config_local.h` (copied from `sample_config_local.h.example`). Note that the macro names on the RTOS side differ from the Linux side:

   | Configuration Item | Type | Required | Meaning and How to Fill In |
   |:---|:---|:---|:---|
   | SAMPLE_APP_ID | string | Yes | Application ID. Fill in the string assigned by the platform. |
   | SAMPLE_APP_NAME | string | No | Application name, i.e., the name entered when creating the application (such as `psdkappfortest`). The server uses it to identify the application; filling it in is recommended. |
   | SAMPLE_APP_KEY | string | Yes | Application key. Keep it safe and do not hard-code it into the repository. |
   | SAMPLE_APP_LICENSE | string | Yes | Application license. |
   | SAMPLE_DEVICE_SN | string | Yes | Serial number of the payload device, customized by the payload developer (**not the aircraft SN**). It identifies the connected payload and also serves as the MQTT connection identifier and the `{client_id}` in each business Topic.<br>Format: digits, letters, and underscores (`_`), no more than 64 characters. Ensure that each payload device uses a unique SN. |
   | SAMPLE_BROKER_ADDR | string | Yes | Address of the broker on the aircraft side. Fill it in according to the aircraft model; for example, it is `192.168.100.3` for the Matrice 5TD. |
   | SAMPLE_BROKER_PORT_TLS | number | Yes | Port used for the TLS connection in the two-phase authentication; default 8883. |
   | SAMPLE_BROKER_PORT | number | Yes | Port used for the plain MQTT connection after token authentication; default 1883. |

   The CA certificate on the RTOS side is embedded in the firmware as a C array and needs no configuration (certificate location: `projects/rtos/gd32f527/network/tls/ca_cert.h`). For where the certificate comes from and how to place it, see <a href="#download-the-certificate">Download the Certificate</a>.
4. **Choose the entry point**: Define `SAMPLE_AUTORUN_ALL=1` (cycle through all) or `SAMPLE_AUTORUN="widget"` (run only one).
5. **Start**: Call `sample_launcher_run(0, NULL)` in a task.

For detailed porting instructions, see the header comments of `samples/launcher/sample_launcher.h` in the SDK package, as well as the `projects/rtos/gd32f527/` reference project.

## Application Binding

After the payload device accesses the MQTT broker, it must first complete **application binding** before the aircraft will allow business requests. When the device is not bound, the aircraft pushes a `bind_required` notification on the event channel and refuses to handle business features such as the speaker and custom widget. For the binding concept and process, see <a href="../app-bind.html" target="_blank" rel="noopener noreferrer">Application Binding</a>.

Before running the demo, please confirm:

1. The payload device has successfully accessed the broker through authentication.
2. Device binding has been completed via DJI Assistant 2.
3. The demo program monitors the binding status, and only starts the business features after confirming that `bind_state` is bound.

For the usage of the interfaces for monitoring and querying the binding status, see <a href="../../function-set/bind.html" target="_blank" rel="noopener noreferrer">Function Set - Binding Status Notification</a>.
