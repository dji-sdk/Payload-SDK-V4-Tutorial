This document is intended for payload developers building on DJI Payload SDK (MQTT), focusing on **how to write code on the SDK side to invoke payload capabilities**: introducing the SDK, configuring access information, establishing a session, creating capability clients, initiating various calls, and finally integrating everything into your own project.

:::tip Note:
This section only covers how to invoke SDK code and is independent of the specific hardware platform. To run a complete Demo on real hardware (which involves hardware connection, creating an application, downloading certificates, compilation, application binding, and running), please first read the corresponding hardware guide: <a href="./quick-demo/raspberry-pi.html" target="_blank" rel="noopener noreferrer">Raspberry Pi (Linux) Quick Start</a> or <a href="./quick-demo/E-Port-V3.html" target="_blank" rel="noopener noreferrer">E‑Port V3 (RTOS) Quick Start</a>.
:::

## Overall Flow

Payload SDK provides C client code. The payload device connects to the aircraft-side broker as an MQTT client and communicates with the flight platform. Writing code on the SDK side to invoke payload capabilities mainly includes the following four steps:

1. **Configure access information**: App ID / App Key / App License / Device SN / broker address / CA certificate.
2. **Establish a session (Session)**: Complete the two-phase authentication to obtain a reusable `ThingModelClientSession_t`.
3. **Create capability clients**: Create a corresponding cap client for each business capability (data_subscription, widget, power, etc.).
4. **Initiate calls**: Call SERVICE / PROPERTY through the client, or subscribe to EVENT / OSD pushes.

The following uses C on the Linux platform as an example, starting from the SDK directory structure, to illustrate the minimal complete flow step by step.

## SDK Package Directory Structure

The release package is **self-contained**: both the protocol code and the C runtime source are bundled, so you can compile without installing any additional tools. The directories relevant to this section are as follows (the directories below are for reference only; the actual directories are subject to the actually released version package):

```
payload-sdk-iot/
├── sdk/
│   ├── generated/c/     Protocol code, organized into subdirectories by capability domain (data_subscription / widget / power / efts / …)
│   └── runtime/c/       Minimal C runtime (session + authentication + transport; host and rtos backends)
│       └── include/     Runtime public header files (thing_model_client/*.h)
├── samples/
│   ├── launcher/        Sample registry, shared session, device information reporting
│   ├── <cap>/src/       Sample source code for each capability domain (such as data_subscription/src/…)
│   └── third_party/     cJSON, mongoose, prebuilt OpenSSL / mosquitto
└── projects/
    ├── linux/           Linux host / aarch64 single-executable project   ← build from here
    └── rtos/gd32f527/   GD32F527 RTOS project
```

When writing code to invoke payload capabilities, you only need to focus on the following three places:

- `sdk/runtime/c/include/thing_model_client/`: Runtime interface headers such as session and OSAL.
- `sdk/generated/c/<cap>/`: The client header files and implementations for each capability domain.
- `samples/<cap>/src/`: Official samples that can be used as a reference when writing your own code.

## Introducing the SDK

Integrating the SDK into a CMake project requires three tasks: **introducing the runtime**, **introducing the protocol code**, and **linking the default implementations correctly**.

### Introducing Header Files

Before writing code, you need to include the runtime session headers as well as the client headers for the required capability domains. Each capability domain corresponds to a directory under `sdk/generated/c/`; for example, `data_subscription/` corresponds to the data subscription feature:

```c
#include "thing_model_client/thing_model_client_session.h"  /* Session facade */
#include "thing_model_client/thing_model_client_osal.h"      /* OSAL registration */
#include "data_subscription/data_subscription_client.h"      /* Capability client */
#include "data_subscription/data_subscription_types.h"       /* Request/reply structs */
#include "common/common_types.h"
```

### Introducing the Runtime and Protocol Code

In the CMake project, introduce the runtime subproject and compile the protocol code of the required capability domains into the target:

```cmake
# 1) Select the platform (host for Linux, rtos for MCU)
set(THING_MODEL_PLATFORM host CACHE STRING "" FORCE)

# 2) Introduce the runtime
add_subdirectory(path/to/sdk/runtime/c _thing_model_runtime)

# 3) Compile the protocol code into the target
file(GLOB_RECURSE TM_GEN_SOURCES path/to/sdk/generated/c/*.c)
add_executable(my_payload main.c ${TM_GEN_SOURCES})
target_include_directories(my_payload PRIVATE
    path/to/sdk/generated/c
    path/to/sdk/runtime/c/include)
```

### Linking the Default Implementations Correctly

The default MQTT transport (mosquitto) and crypto (openssl) implementations are registered via **weak-symbol factories**, so they must be fully linked with `--whole-archive`; otherwise the runtime will fail to connect due to missing implementations:

```cmake
target_link_libraries(my_payload PRIVATE
    -Wl,--whole-archive
    thing_model_client_transport_mosquitto
    thing_model_client_crypto_openssl
    -Wl,--no-whole-archive
    thing_model_client_runtime
    pthread)
```

:::warning Note:
`--whole-archive` must not be omitted. Without this option, the default mosquitto transport and openssl crypto implementations will not be pulled in by the linker.
:::

To port to your own protocol stack or replace the default transport or crypto implementation, you can inject a custom vtable in the session configuration. The interface definitions are in `sdk/runtime/c/include/thing_model_client/thing_model_client_transport.h` and `..._crypto.h`.

## Configuring Access Information

Establishing a session requires a set of access credentials, including App ID, App Name, App Key, App License, Device SN, broker address, and CA certificate. This information comes from <a href="./quick-demo/raspberry-pi.html#创建应用" target="_blank" rel="noopener noreferrer">Create an Application</a> and <a href="./quick-demo/raspberry-pi.html#下载证书" target="_blank" rel="noopener noreferrer">Download Certificate</a>. For the type, whether required, and how to fill in each field, see <a href="./quick-demo/raspberry-pi.html#补充应用信息" target="_blank" rel="noopener noreferrer">Supplement Application Information</a>.

In the sample project, the above values are filled in centrally in `projects/linux/sample_config_local.h`; at runtime they can also be overridden by environment variables of the same name `THING_MODEL_*` (priority: environment variable > local header file > placeholder default in source). Do not commit real App Key / App License values into version control.

:::warning Note:
The CA certificate path must be a **real, readable absolute path**. This is the most common issue on first access. If it is still the placeholder `/path/to/ca.crt`, the TLS handshake will fail directly when loading the trust chain.
:::

## Establishing a Session (Session)

`ThingModelClientSession_t` is the **session facade**. All cap clients share the same session, which is responsible for topic subscription, message dispatch, and reconnection.

### Two-Phase Authentication

The access process includes two rounds of authentication, which are performed automatically inside `ThingModelClientSession_Connect()`:

1. **Authentication based on application credentials (Phase 1)**: Connect to broker port 8883 via TLS, complete authentication with application credentials over the encrypted channel, export RFC 5705 keying material as the HMAC key, and then disconnect.
2. **Token-based authentication (Phase 2)**: Use `HMAC-SHA256(key, SN)` to generate a token, connect to broker port 1883 (plain MQTT), and append a timestamp and HMAC signature to the tail of subsequent publish packets.

TLS is used only to encrypt the transport channel and verify the broker's server certificate; it does not by itself constitute authentication of the payload's identity. **Both ports 8883 and 1883 must be reachable**; the log will show `Phase1 ...` followed by `Phase2 connected, session ready`.

### Establishing and Releasing

First register an OSAL (Linux uses the built-in POSIX implementation), then fill in the configuration and connect:

```c
/* 1. Register the POSIX OSAL (Linux) */
ThingModelOsal_RegisterPosix();

/* 2. Fill in the session configuration */
ThingModelClientSession_Config_t cfg = {
    .app_id          = "YOUR_APP_ID",
    .app_name        = "psdkappfortest",
    .app_key         = "YOUR_APP_KEY",
    .app_license     = "YOUR_APP_LICENSE",
    .device_sn       = "SN1234567890",
    .broker_address  = "192.168.100.3",
    .broker_port_tls = 8883,
    .broker_port     = 1883,
    .ca_cert_path    = "/absolute/path/ca.crt",
    .topic_style     = THING_MODEL_TOPIC_STYLE_V2,  /* V2 by default */
    .auto_reconnect  = true,                        /* reconnect on disconnect is recommended */
    .reconnect_delay_min_sec = 1,
    .reconnect_delay_max_sec = 30,
};

/* 3. Connect (two-phase authentication is done internally) */
ThingModelClientSession_t *s = ThingModelClientSession_Connect(&cfg);
if (!s) {
    const T_ThingModelLastError *e = ThingModelClientSession_GetLastError();
    fprintf(stderr, "connect failed: rc=%d %s\n", e->rc, e->message);
    return -1;
}

/* ... create clients, initiate calls ... */

ThingModelClientSession_Disconnect(s);
```

:::tip Note:
When a connection fails, in addition to checking whether `Connect()` returns NULL, it is recommended to call `ThingModelClientSession_GetLastError()` to get `rc` / `transport_rc` / `errno` and a textual description, so that you can locate the problem more accurately.
:::

## Creating Capability Clients

Each business capability corresponds to a client struct, created via `<Cap>_CreateClient(session)` and released via `<Cap>_DestroyClient()`. All clients are based on the same session:

```c
Speaker_Client_t          *spk = Speaker_CreateClient(s);
DataSubscription_Client_t *ds  = DataSubscription_CreateClient(s);
Widget_Client_t           *w   = Widget_CreateClient(s);
```

The client internally subscribes to the reply / event / osd topics required by that capability. Business code only needs to call the synchronous or asynchronous APIs it provides, without worrying about the underlying topics and JSON encoding/decoding.

## Initiating Calls

The interfaces under each capability domain fall into four call forms:

| Type | Description | Typical API Example |
|:---|:---|:---|
| **SERVICE** | Request the device to perform an action and wait for a reply | `DataSubscription_SubscribeTopic(ds, &req, &resp, 5000)` |
| **PROPERTY** | Read or set device parameters | `Widget_SetValue(w, &req, &resp, 5000)` |
| **EVENT** | Subscribe to occasional events | `Widget_OnFloatWindowMsg(w, cb, NULL)` |
| **OSD** | Subscribe to periodic reports | `DataSubscription_OnPublishData(ds, cb, NULL)` |

Among these, SERVICE / PROPERTY usually provide three sets of APIs that you can choose according to the scenario:

- **Synchronous**: `Widget_SetValue(w, &req, &resp, timeout)` — publish and block waiting for the reply.
- **Asynchronous**: `Widget_SetValueAsync(w, &req, cb, user)` — return immediately after registering the callback.
- **Pure construction**: `Widget_BuildSetValuePayload(style, seq, &req)` — only generate the JSON string without publishing, suitable for unit testing without a broker or integrating with a custom transport.

### SERVICE Call Example

Taking data subscription as an example, subscribe to an FC telemetry topic and then query its latest value. This example is a read-only operation that does not issue any flight control commands, making it suitable as the first access verification:

```c
/* Subscribe to an FC telemetry topic */
T_DataSubscriptionSubscribeTopicRequest sub = {0};
sub.topic     = "quaternion";
sub.frequency = DATA_SUBSCRIPTION_FREQUENCY_1HZ;
T_ThingModelCommonReply sub_resp = {0};
T_ThingModelReturnCode rc = DataSubscription_SubscribeTopic(ds, &sub, &sub_resp, 5000);

/* Query the latest value of this topic */
T_DataSubscriptionGetLatestValueRequest q = {0};
q.topic = "quaternion";
T_ThingModelCommonReply q_resp = {0};
rc = DataSubscription_GetLatestValue(ds, &q, &q_resp, 5000);
printf("GetLatestValue rc=%d result=%d\n", rc, q_resp.result);
```

The complete client header files for each capability domain are located in `sdk/generated/c/<cap>/` within the SDK package, where you can look up all the SERVICE / PROPERTY / EVENT / OSD interfaces it provides.

## Writing Your First Complete Program

Combining the above steps produces a runnable minimal program: connect to the broker, create a `DataSubscription` client, and call a read-only SERVICE to complete the first verification.

```c
#include "thing_model_client/thing_model_client_session.h"
#include "thing_model_client/thing_model_client_osal.h"
#include "data_subscription/data_subscription_client.h"
#include "data_subscription/data_subscription_types.h"
#include "common/common_types.h"
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static const char *envdef(const char *k, const char *d) {
    const char *v = getenv(k);
    return (v && *v) ? v : d;
}

int main(int argc, char **argv)
{
    (void)argc; (void)argv;

    /* 1. Register the POSIX OSAL */
    ThingModelOsal_RegisterPosix();

    /* 2. Configure the session (read from THING_MODEL_* environment variables first) */
    ThingModelClientSession_Config_t cfg = {
        .app_id          = envdef("THING_MODEL_APP_ID",       "YOUR_APP_ID"),
        .app_name        = envdef("THING_MODEL_APP_NAME",     "psdkappfortest"),
        .app_key         = envdef("THING_MODEL_APP_KEY",      "YOUR_APP_KEY"),
        .app_license     = envdef("THING_MODEL_APP_LICENSE",  "YOUR_APP_LICENSE"),
        .device_sn       = envdef("THING_MODEL_DEVICE_SN",    "SN1234567890"),
        .broker_address  = envdef("THING_MODEL_BROKER",       "127.0.0.1"),
        .broker_port_tls = 8883,
        .broker_port     = 1883,
        .ca_cert_path    = envdef("THING_MODEL_CA_CERT_PATH", "/path/to/ca.crt"),
        .topic_style     = THING_MODEL_TOPIC_STYLE_V2,
    };

    ThingModelClientSession_t *s = ThingModelClientSession_Connect(&cfg);
    if (!s) {
        fprintf(stderr, "session connect failed\n");
        return 1;
    }

    /* 3. Create the DataSubscription client */
    DataSubscription_Client_t *ds = DataSubscription_CreateClient(s);

    /* 4. Subscribe to an FC telemetry topic */
    T_DataSubscriptionSubscribeTopicRequest sub = {0};
    sub.topic     = "quaternion";
    sub.frequency = DATA_SUBSCRIPTION_FREQUENCY_1HZ;
    T_ThingModelCommonReply sub_resp = {0};
    T_ThingModelReturnCode rc = DataSubscription_SubscribeTopic(ds, &sub, &sub_resp, 5000);
    if (rc != THING_MODEL_RC_OK) {
        printf("SubscribeTopic failed, rc=%d\n", rc);
    } else {
        printf("SubscribeTopic result=%d\n", sub_resp.result);
    }

    /* 5. Query the latest value of this topic */
    T_DataSubscriptionGetLatestValueRequest q = {0};
    q.topic = "quaternion";
    T_ThingModelCommonReply q_resp = {0};
    rc = DataSubscription_GetLatestValue(ds, &q, &q_resp, 5000);
    printf("GetLatestValue rc=%d result=%d\n", rc, q_resp.result);

    /* 6. Clean up */
    DataSubscription_DestroyClient(ds);
    ThingModelClientSession_Disconnect(s);
    return 0;
}
```

## Integrating the SDK into Your Own Project

### Modifying Based on the Sample Project

It is recommended to first get the complete example in `projects/linux` of the SDK package running, then add your own `.c` files under that project:

1. Copy an existing sample directory (such as `samples/data_subscription/`) and rename it to your payload capability directory.
2. Modify the `CMakeLists.txt` under that directory to adjust the source files and the executable name.
3. Register your sample in the top-level `projects/linux/CMakeLists.txt`.
4. Write `src/your_client_demo.c`, referring to `samples/data_subscription/src/data_subscription_client_demo.c` or `samples/widget/src/widget_client_demo.c`.

Without a broker, you can also first use the **pure construction API** to verify JSON generation, then debug on real hardware.

### Standalone CMake Project

To use the SDK directly in your own repository, refer to the CMake snippets in <a href="#introducing-the-sdk">Introducing the SDK</a>, add `sdk/runtime/c` and the required `sdk/generated/c/<cap>/` to the project, and complete linking according to the weak-symbol rule. For more details, see the `README.md` in the SDK package.

### Running the First Executable

After completing the code, build in the SDK package root directory. Host (x86_64) compilation is used to quickly verify the SDK code logic; if the target platform is aarch64 (such as Raspberry Pi 4B or Manifold), please use cross-compilation instead (see <a href="./quick-demo/raspberry-pi.html" target="_blank" rel="noopener noreferrer">Raspberry Pi Quick Start</a>).

```bash
cmake -B build_host -S projects/linux -DSAMPLE_BUILD=host
cmake --build build_host -j
./build_host/sample_things_model --list        # list the samples in this package
./build_host/sample_things_model data_subscription   # running data subscription first is recommended for the first verification
```

## Debugging Tips

### Viewing the Topic and JSON of Each Call

After setting the log level to `debug`, stderr prints the complete topic and JSON of each publish and received message, making it easy to reconcile with the aircraft-side protocol:

```bash
export THING_MODEL_LOG_LEVEL=debug
./sample_things_model widget --debug
```

### Constructing JSON Only (Without Connecting to the Broker)

Using the pure construction API, you can first verify that the payload generation is correct without a broker:

```c
T_WidgetSetValueRequest req = { .widget_index = 0, .widget_type = 1, .widget_value = 1 };
char *json = Widget_BuildSetValuePayload(THING_MODEL_TOPIC_STYLE_V2, 42, &req);
printf("%s\n", json);
free(json);
```

### Common Return Codes

The synchronous API returns `T_ThingModelReturnCode`, which indicates the call result at the **SDK / network layer**:

| Value | Meaning |
|:---|:---|
| `THING_MODEL_RC_OK` (0) | The SDK-level call succeeded; you still need to check `resp.result` |
| `THING_MODEL_RC_TIMEOUT` (-3) | The device did not reply within the timeout |
| `THING_MODEL_RC_TRANSPORT_ERROR` (-4) | MQTT-layer error; broker unreachable or connection refused |
| `THING_MODEL_RC_AUTH_FAILED` (-5) | Access authentication failed; check App Key / License / SN / CA certificate |

**Business-layer errors** are reflected in `resp.result != 0`, so the two layers must be judged separately:

```c
if (rc != THING_MODEL_RC_OK) {
    printf("SDK/network error: %d\n", rc);
} else if (resp.result != 0) {
    printf("Device rejected: %d %s\n", resp.result, resp.result_message);
} else {
    printf("OK\n");
}
```
