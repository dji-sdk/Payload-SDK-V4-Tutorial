A payload device must connect to the aircraft-side broker before it can send or receive any service messages. This section describes the low-level protocol used by a payload device to securely access the MQTT server (Secure Access). It covers three parts: the connection parameters, the message construction rules for the two authentication steps, and the integrity verification mechanism for service messages.

:::tip Note:
The C interfaces in PSDK encapsulate the MQTT protocol described in this section. When developing with PSDK, you do not need to handle MQTT messages directly. Refer to these protocol definitions only if you need to implement the protocol yourself or debug and verify the access process. For the feature overview and C interface examples, see <a href="../function-set/access-authentication.html" target="_blank" rel="noopener noreferrer">Function Set - Access and Authentication</a>.
:::

## Connection Overview

The access process requires establishing two connections in sequence, each completing one authentication:

| Connection | Port | Transport channel | Authentication method | Purpose |
|:---|:---|:---|:---|:---|
| Connection&nbsp;1 | 8883 | TLS | Based on application credentials | Verify the application credentials over the encrypted TLS channel and export the keying material bound to this connection; the connection is then closed. |
| Connection&nbsp;2 | 1883 | Plain MQTT | Based on token | Compute the token using the keying material exported from Connection 1 to connect to the broker and establish the persistent service connection. All subsequent service messages reuse this connection. |

:::warning Warning:
TLS is used only to encrypt the transport channel and verify the broker's server certificate. It does not authenticate the payload identity by itself. Payload identity authentication is completed by the two authentication steps listed in the table above.
:::

Both connections are initiated by the payload to the aircraft. For both connections, the MQTT client identifier `{client_id}` is the payload device serial number, and QoS is 0.

## Connection Parameters

The parameters required for access are listed below. Among them, `app_id`, `app_name`, `app_key`, and `app_license` are the application credentials; for how to obtain them, see <a href="../payload-quick-start/quick-demo/raspberry-pi.html#obtaining-application-information" target="_blank" rel="noopener noreferrer">Obtaining Application Information</a>. The rest are device and connection information.

| Parameter | Type | Required | Meaning and value |
|:---|:---|:---|:---|
| app_id | string | Yes | Application ID; the string assigned by the platform. |
| app_name | string | No | Application name, i.e., the name entered when creating the application (such as `psdkappfortest`). The server identifies the application by this name; providing it is recommended. |
| app_key | string | Yes | Application key. |
| app_license | string | Yes | Application license. |
| device_sn | string | Yes | Serial number of the payload device, customized by the payload developer (**not the aircraft SN**). It identifies the connected payload and is used as both the MQTT client identifier `{client_id}` and the `{client_id}` in each service topic.<br>Format: digits, letters, and underscores (`_`), no more than 64 characters. Each payload client must use a unique `device_sn`. |
| broker_address | string | Yes | Address of the aircraft-side broker. The value depends on the aircraft model; for example, Matrice 5TD is `192.168.100.3`. |
| broker_port_tls | int | Yes | Port for the TLS connection (Connection 1); the value is `8883`. |
| broker_port | int | Yes | Port for the plain MQTT connection (Connection 2); the value is `1883`. |
| ca_cert_path | string | Yes | Path to the CA certificate (`ca.crt`), used to verify the broker's server certificate. For how to obtain the certificate, see <a href="../payload-quick-start/quick-demo/raspberry-pi.html#download-the-certificate" target="_blank" rel="noopener noreferrer">Download the Certificate</a>. |

## Connection 1: Authentication Based on Application Credentials

The payload connects to port `8883` of the broker over TLS, and constructs the MQTT username and password according to the following rules. After authentication succeeds, 32 bytes of keying material (hereinafter `hmac_key`) are exported from the TLS session for use by Connection 2; the connection is then closed.
```text
username: {app_id}:{app_name}_psdk_{device_sn}    # {app_id}_psdk_{device_sn} when app_name is absent
password: {app_key}_{app_license}_{timestamp_ms}  # timestamp_ms is the client millisecond timestamp, used for replay protection
```

The `hmac_key` is obtained through TLS keying material export (RFC 5705 keying material) and is bound to this TLS session.

## Connection 2: Authentication Based on Token

The payload connects to port `1883` of the broker over plain MQTT, and constructs the MQTT username and password according to the following rules:

```text
username: token:{hex(HMAC-SHA256(hmac_key, device_sn))}
password:                                               # empty
```

Once Connection 2 is established, it becomes the persistent service connection. All subsequent service topics are sent and received over this connection.

## Service Message Integrity Verification

After Connection 2 is established, each service message published by the payload (PUBLISH) must append a millisecond timestamp and an HMAC signature to the end of the original payload, so that the server can verify the integrity and timeliness of the message. Messages received via subscription (SUBSCRIBE) do not contain this structure.

:::tip Note:
This mechanism provides **tamper protection** (any modification of the message in transit causes the HMAC verification to fail) and **replay protection** (an old message is rejected because its timestamp has expired).
:::

The byte layout of a published message is: **original payload ‖ 8-byte timestamp (big-endian) ‖ 32-byte HMAC**. Each part is described below:

- `‖` denotes byte concatenation (joined end to end).
- **8-byte timestamp**: the millisecond time at the moment of sending, stored in big-endian order (most significant byte first).
- **32-byte HMAC**: the message authentication code, computed with HMAC-SHA256 over the preceding "payload ‖ timestamp" using the key `hmac_key` (exported during Connection 1 authentication).

```text
final published bytes = payload || ts_be8 || HMAC32
where  HMAC32 = HMAC-SHA256(key = hmac_key, message = payload || ts_be8)
```

Taking the service JSON `{"seq":1,"method":"efts_get_fts_trigger_status","data":{}}` and the send time `ts = 1753689600000` (0x0001987B8E5A6800) as an example, the message actually published to MQTT (with the appended tail shown in hexadecimal) is:

```text
[original payload, 53 bytes]
7B 22 73 65 71 22 3A 31 ... 7D          # {"seq":1,...,"data":{}}
[+ 8-byte timestamp, big-endian]
00 01 98 7B 8E 5A 68 00                  # ts = 1753689600000
[+ 32-byte HMAC-SHA256(hmac_key, payload||ts)]
a3 f1 c9 ... (32 bytes total)           # the server recomputes and compares using the same hmac_key
```

After receiving the message, the server recomputes the HMAC over "payload ‖ ts" using `hmac_key` following the same rules, and compares it with the 32 bytes at the end of the message: a match indicates that the message is intact and untampered. It also verifies the timestamp, and messages outside the valid time window (such as a recorded message being replayed) are rejected.
