This section defines the MQTT interfaces of the local upgrade feature, covering the MQTT payload structures and field descriptions for entering upgrade mode, verifying firmware, starting upgrade, finishing upgrade, and pushing upgrade status.

:::tip Note:
- The C interfaces in PSDK encapsulate the MQTT protocol described in this section. When developing with PSDK, you do not need to handle MQTT messages directly. Refer to these protocol definitions only if you need to implement the protocol yourself or debug and verify the underlying messages. For the feature overview and C interface examples, see <a href="../function-set/local-update.html" target="_blank" rel="noopener noreferrer">Function Set - Local Upgrade</a>.
- Before using this feature, the payload device must first complete access and authentication. For the access protocol, see <a href="api-access-authentication.html" target="_blank" rel="noopener noreferrer">Access and Authentication</a>.
:::

## Protocol Description

The Topics involved in the interfaces are as follows:

| Type | Direction | Topic |
|:---|:---|:---|
| service request | aircraft → payload | thing/product/{client_id}/services |
| service response | payload → aircraft | thing/product/{client_id}/services_reply |
| event push | payload → aircraft | thing/product/{client_id}/events |

- `{client_id}` is the payload device serial number.
- **QoS**: 0.

The interfaces supported by this module are as follows:

| method | Type | Purpose | Corresponding C interface |
|:---|:---|:---|:---|
| upgrade_enter_upgrade_mode | service | Aircraft requests the payload to enter upgrade mode | UpgradeImpl_OnEnterUpgradeMode() |
| upgrade_check_firmware | service | Aircraft requests the payload to verify firmware | UpgradeImpl_OnCheckFirmware() |
| upgrade_start_upgrade | service | Aircraft instructs the payload to start upgrade | UpgradeImpl_OnStartUpgrade() |
| upgrade_finish_upgrade | service | Aircraft notifies the end of the upgrade sequence | UpgradeImpl_OnFinishUpgrade() |
| upgrade_push_upgrade_state | event | Payload pushes the upgrade state | Upgrade_PublishPushUpgradeState() |

:::warning Warning:
The upgrade commands have a strict timing order: the aircraft sends `upgrade_enter_upgrade_mode` → `upgrade_check_firmware` → `upgrade_start_upgrade` → `upgrade_finish_upgrade` in sequence. After receiving `upgrade_start_upgrade`, the payload should reply immediately, then execute the upgrade in the background and continuously report the upgrade state via `upgrade_push_upgrade_state`; after receiving `upgrade_finish_upgrade`, it stops pushing. The firmware body is transferred over HTTP (provided by the `url` in the enter upgrade mode response) and does not go through the MQTT channel.
:::

## Common Parameters

The following parameters are the top-level common parameters shared by the requests and responses of the upgrade interfaces, and are not repeated in the field descriptions of each interface.

### Request Parameters

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| seq | integer | Yes | Request sequence number; echoed back unchanged in the response, used to match request and response. |
| method | string | Yes | Method identifier; for values, see each interface description. |
| data | object | Yes | Service data body; `{}` when there are no service parameters. |

### Response Parameters

The top-level fields of the response are the same as the request. `data` includes the following common fields by default; for interface-specific fields, see the corresponding section.

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| result | integer | Yes | Processing result.<ul><li>0: Success</li><li>Non-zero: Failure</li></ul> |
| result_message | string | Yes | Result description message. |

## Enter Upgrade Mode

The aircraft requests the payload to enter upgrade mode. In its reply, the payload returns the number of seconds the aircraft should wait and the firmware download address, based on which the aircraft obtains the firmware over HTTP.

Related feature section: <a href="../function-set/local-update.html#enter-upgrade-mode" target="_blank" rel="noopener noreferrer">Enter Upgrade Mode</a>.

### Request Payload Example

- **Topic**: `thing/product/{client_id}/services`
- **Direction**: aircraft → payload
- **QoS**: 0
- **method**: `upgrade_enter_upgrade_mode`
- **Corresponding interface**: `UpgradeImpl_OnEnterUpgradeMode()`

```json
{
  "seq": 1,
  "method": "upgrade_enter_upgrade_mode",
  "data": {}
}
```

### Request Field Description

For the top-level fields, see [Request Parameters](#request-parameters); `data` is a fixed empty object `{}`.

### Response Payload Example

- **Topic**: `thing/product/{client_id}/services_reply`
- **Direction**: payload → aircraft

```json
{
  "seq": 1,
  "method": "upgrade_enter_upgrade_mode",
  "data": {
    "result": 0,
    "result_message": "success",
    "wait_time": 10,
    "url": "http://192.168.1.10:8000/upgrade.bin"
  }
}
```

### Response Field Description

For the top-level fields, see [Response Parameters](#response-parameters); the `data` field description is as follows:

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| wait_time | integer | Yes | The number of seconds the aircraft should wait, used for the payload to prepare the storage area and other preparatory operations. |
| url | string | Yes | Firmware download address; the aircraft obtains the firmware from this address over HTTP, e.g., `http://<device-ip>:8000/upgrade.bin`. |

## Upgrade State Push

The payload pushes the current upgrade state during the upgrade execution, including the upgrade progress and result.

Related feature section: <a href="../function-set/local-update.html#upgrade-state-push" target="_blank" rel="noopener noreferrer">Upgrade State Push</a>.

### Payload Example

- **Topic**: `thing/product/{client_id}/events`
- **Direction**: payload → aircraft
- **QoS**: 0
- **method**: `upgrade_push_upgrade_state`
- **Corresponding interface**: `Upgrade_PublishPushUpgradeState()`

```json
{
  "seq": 5,
  "method": "upgrade_push_upgrade_state",
  "data": {
    "upgrade_stage": 3,
    "value": 50
  }
}
```

### Field Description

For the top-level fields, see [Request Parameters](#request-parameters); the `data` field description is as follows:

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| upgrade_stage | integer | Yes | Upgrade stage.<ul><li>0: Idle, no upgrade in progress</li><li>3: Upgrading</li><li>4: Upgrade completed</li><li>6: Device rebooting</li></ul> |
| value | integer | Yes | Meaning varies with upgrade_stage.<ul><li>Upgrading (3): upgrade progress, value 0~100</li><li>Upgrade completed (4): upgrade result, 1 for success, 2 for failure</li><li>Device rebooting (6): reboot timeout in seconds, value 0~255</li></ul> |

:::warning Warning:
The meaning of the `value` field depends on `upgrade_stage`; when parsing, first determine the stage and then interpret the value. In the upgrade completed stage (4), `value` is the upgrade result (1 success / 2 failure) and should not be confused with the upgrade progress (0~100).
:::
