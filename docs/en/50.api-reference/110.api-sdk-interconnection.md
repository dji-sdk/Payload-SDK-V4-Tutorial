This section defines the MQTT control-plane interfaces of the MOP data channel for SDK Interconnection, covering the MQTT payload structures and field descriptions for enabling a channel, disabling a channel, and pushing channel status.

The MOP data channel uses a dual-plane architecture. The MQTT interface is the control plane, which negotiates the target device and channel parameters, returns the TCP data-plane endpoint, and pushes channel status. The actual application data is sent and received over the TCP socket on the data plane, not over MQTT. Control-plane interaction is bidirectional: the payload sends service commands to enable or disable a channel, and the aircraft pushes channel status through events.

:::tip Note:
- The C interfaces in PSDK encapsulate the MQTT protocol described in this section. When developing with PSDK, you do not need to handle MQTT messages directly. Refer to these protocol definitions only if you need to implement the protocol yourself or debug and verify the underlying messages. For the feature overview and C interface examples, see <a href="../function-set/sdk-interconnection.html" target="_blank" rel="noopener noreferrer">Function Set - SDK Interconnection</a>.
- Before using this feature, the payload device must first complete Access and Authentication. For the access protocol, see <a href="api-access-authentication.html" target="_blank" rel="noopener noreferrer">Access and Authentication</a>.
:::

:::warning Warning:
The MOP data plane is based on POSIX TCP sockets, supports only Linux, and requires aircraft firmware that supports MOP channels. This section only defines the MQTT protocol of the control plane. The TCP connection and data-plane sending and receiving are implemented by the payload itself.
:::

## Protocol Description

The Topics involved in the interfaces are as follows:

| Type | Direction | Topic |
|:---|:---|:---|
| service request | payload → aircraft | `thing/product/{client_id}/services` |
| service response | aircraft → payload | `thing/product/{client_id}/services_reply` |
| event push | aircraft → payload | `thing/product/{client_id}/events` |

- `{client_id}` is the payload device serial number.
- **QoS**: 0.

The interfaces supported by this module are as follows:

| method | Type | Purpose | Corresponding C interface |
|:---|:---|:---|:---|
| `mop_channel_enable` | service | The payload enables the data channel and obtains the TCP data plane endpoint | `MopChannel_Enable()` |
| `mop_channel_disable` | service | The payload disables the data channel | `MopChannel_Disable()` |
| `mop_channel_event` | event | The aircraft pushes the channel status to the payload (ACTIVE, CLOSED) | `MopChannel_OnChannelEvent()` |

:::warning Warning:
Complete channel lifecycle: the payload sends `mop_channel_enable` → the aircraft replies with `ip` / `port` / `state:"listening"` → the payload establishes the TCP connection → the aircraft pushes `mop_channel_event` (state=1 ACTIVE) → data plane send/receive → the payload sends `mop_channel_disable` → the aircraft pushes `mop_channel_event` (state=2 CLOSED) → the payload closes the socket. The channel ID is not restricted to a fixed value range; communication can be established as long as both ends agree to use the same channel number.
:::

## Common Parameters

The following parameters are the top-level common parameters shared by the messages of all MOP interfaces, and are not listed repeatedly in the field descriptions of each interface.

### Request Parameters

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| seq | integer | Yes | Request sequence number; echoed back unchanged in the response, used to match the request with the response. |
| method | string | Yes | Method identifier; for values, see each interface description. |
| data | object | Yes | Service data body; `{}` when there are no service parameters. |

### Response Parameters

The top-level fields of the response are the same as those of the request. See the corresponding sections for the `data` fields of each interface.

## Enable Channel

The payload enables the data channel. The aircraft returns the channel status and the TCP data plane endpoint (ip / port) in the response, based on which the payload establishes the TCP connection.

Related feature section: <a href="../function-set/sdk-interconnection.html#enable-channel" target="_blank" rel="noopener noreferrer">Enable Channel</a>.

### Request Payload Example

- **Topic**: `thing/product/{client_id}/services`
- **Direction**: payload → aircraft
- **QoS**: 0
- **method**: `mop_channel_enable`
- **Corresponding interface**: `MopChannel_Enable()`

```json
{
  "seq": 1,
  "method": "mop_channel_enable",
  "data": {
    "role": 1,
    "reliability": 0,
    "channel_id": 49153,
    "target_device_type": 3,
    "target_address": 1
  }
}
```

### Request Field Description

For the top-level fields, see [Request Parameters](#request-parameters). The `data` fields are described as follows:

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| role | integer | Yes | Channel role.<ul><li>0: ROLE_SERVER, listens and waits for the peer to connect</li><li>1: ROLE_CLIENT, actively connects to the peer</li></ul> |
| reliability | integer | Yes | Data plane transmission type.<ul><li>0: RELIABILITY_RELIABLE, reliable transmission</li><li>1: RELIABILITY_UNRELIABLE, unreliable transmission</li></ul> |
| channel_id | integer | Yes | Channel ID; communication can be established as long as both ends agree to use the same channel number. |
| target_device_type | integer | Yes | Target device SDK type.<ul><li>1: TARGET_DEVICE_TYPE_MSDK, mobile</li><li>2: TARGET_DEVICE_TYPE_OSDK, onboard</li><li>3: TARGET_DEVICE_TYPE_PSDK, payload</li></ul> |
| target_address | integer | Yes | Target address.<ul><li>client mode: target payload position 1, 2, 3</li><li>server mode: fixed to 0</li></ul> |

### Response Payload Example

- **Topic**: `thing/product/{client_id}/services_reply`
- **Direction**: aircraft → payload

```json
{
  "seq": 1,
  "method": "mop_channel_enable",
  "data": {
    "result": 0,
    "result_message": "success",
    "channel_id": 49153,
    "state": "listening",
    "ip": "192.168.1.1",
    "port": 12345
  }
}
```

### Response Field Description

For the top-level fields, see [Response Parameters](#response-parameters). The `data` fields are described as follows:

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| result | integer | Yes | Processing result.<ul><li>0: Success</li><li>Non-zero: Failure</li></ul> |
| result_message | string | Yes | Result description message. |
| channel_id | integer | Yes | Channel ID. |
| state | string | Yes | Channel status, `listening` on success. |
| ip | string | Yes | IP address of the TCP data plane endpoint, based on which the payload establishes the TCP connection. |
| port | integer | Yes | Port of the TCP data plane endpoint. |

## Disable Channel

The payload disables the data channel. The service response is empty; the channel closure is confirmed by the channel status push `mop_channel_event` (state=2 CLOSED).

Related feature section: <a href="../function-set/sdk-interconnection.html#disable-channel" target="_blank" rel="noopener noreferrer">Disable Channel</a>.

### Request Payload Example

- **Topic**: `thing/product/{client_id}/services`
- **Direction**: payload → aircraft
- **QoS**: 0
- **method**: `mop_channel_disable`
- **Corresponding interface**: `MopChannel_Disable()`

```json
{
  "seq": 2,
  "method": "mop_channel_disable",
  "data": {
    "channel_id": 49153
  }
}
```

### Request Field Description

For the top-level fields, see [Request Parameters](#request-parameters). The `data` fields are described as follows:

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| channel_id | integer | Yes | The channel ID to be disabled. |

### Response Payload Example

- **Topic**: `thing/product/{client_id}/services_reply`
- **Direction**: aircraft → payload

```json
{
  "seq": 2,
  "method": "mop_channel_disable",
  "data": {}
}
```

### Response Field Description

For the top-level fields, see [Response Parameters](#response-parameters). The response `data` is an empty object `{}`. The actual channel closure is confirmed by the [Channel Status Push](#channel-status-push) delivering the `CLOSED` status.

## Channel Status Push

The aircraft pushes channel status changes. It pushes `ACTIVE` when the channel is ready, and `CLOSED` when the channel is closed.

Related feature section: <a href="../function-set/sdk-interconnection.html#receive-channel-status" target="_blank" rel="noopener noreferrer">Receive Channel Status</a>.

### Payload Example

- **Topic**: `thing/product/{client_id}/events`
- **Direction**: aircraft → payload
- **QoS**: 0
- **method**: `mop_channel_event`
- **Corresponding interface**: `MopChannel_OnChannelEvent()`

```json
{
  "seq": 3,
  "method": "mop_channel_event",
  "data": {
    "channel_id": 49153,
    "state": 1
  }
}
```

### Field Description

For the top-level fields, see [Request Parameters](#request-parameters). The `data` fields are described as follows:

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| channel_id | integer | Yes | Channel ID. |
| state | integer | Yes | Channel status.<ul><li>1: ACTIVE, the data plane is ready and TCP send/receive can start</li><li>2: CLOSED, the channel is closed and the TCP socket should be safely closed</li></ul> |

:::warning Warning:
A `state` of 1 (ACTIVE) indicates that the data plane is ready and the payload can start TCP send/receive; a value of 2 (CLOSED) indicates that the channel is closed and the payload should safely close the TCP socket. If CLOSED is received while waiting for ACTIVE, it usually indicates that the peer device is not ready.
:::
