This section defines the MQTT interfaces of the power management feature, covering the MQTT payload structures and field descriptions for power-off notifications.

:::tip Note:
- The C interfaces in PSDK encapsulate the MQTT protocol described in this section. When developing with PSDK, you do not need to handle MQTT messages directly. Refer to these protocol definitions only if you need to implement the protocol yourself or debug and verify the underlying messages. For the feature overview and C interface examples, see <a href="../function-set/power-management.html" target="_blank" rel="noopener noreferrer">Function Set - Power Management</a>.
- Before using this feature, the payload device must first complete Access and Authentication. For the access protocol, see <a href="api-access-authentication.html" target="_blank" rel="noopener noreferrer">Access and Authentication</a>.
:::

## Protocol Description

The Topics involved in the interfaces are as follows:

| Type | Topic |
|:---|:---|
| service request | thing/product/{client_id}/services |
| service response | thing/product/{client_id}/services_reply |

- `{client_id}` is the payload device serial number.
- **QoS**: 0.

See the corresponding section for the direction of the interface:

| method | Type | Purpose | Direction | Corresponding C interface |
|:---|:---|:---|:---|:---|
| power_off_notification | service | The aircraft notifies the payload to prepare for power off | aircraft → payload | PowerImpl_OnPowerOffNotification() |

## Common Parameters

The following parameters are the top-level common parameters shared by the requests and responses of all power management interfaces, and are not listed repeatedly in the field descriptions of each interface.

### Request Parameters

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| seq | integer | Yes | Request sequence number; echoed back unchanged in the response, used to match the request with the response. |
| method | string | Yes | Method identifier; for values, see each interface description. |
| data | object | Yes | Service data body; `{}` when there are no service parameters. |

### Response Parameters

The top-level fields of the response are the same as those of the request. `data` contains the following common fields by default; interface-specific fields are described in the corresponding sections.

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| result | integer | Yes | Processing result.<ul><li>0: Success</li><li>Non-zero: Failure</li></ul> |
| result_message | string | Yes | Result description message. |

## Power-Off Notification

The aircraft notifies the payload that it is about to power off. The payload returns whether it is ready to power off in the response.

Related feature section: <a href="../function-set/power-management.html#respond-to-power-off-notification" target="_blank" rel="noopener noreferrer">Respond to Power-off Notification</a>.

### Request Payload Example

- **Topic**: `thing/product/{client_id}/services`
- **Direction**: aircraft → payload
- **QoS**: 0
- **method**: `power_off_notification`
- **Corresponding interface**: `PowerImpl_OnPowerOffNotification()`

```json
{
  "seq": 2,
  "method": "power_off_notification",
  "data": {}
}
```

### Request Field Description

For the top-level fields, see [Request Parameters](#request-parameters). `data` is fixed as an empty object `{}`.

### Response Payload Example

- **Topic**: `thing/product/{client_id}/services_reply`
- **Direction**: payload → aircraft

```json
{
  "seq": 2,
  "method": "power_off_notification",
  "data": {
    "result": 0,
    "result_message": "success",
    "preparation_flag": true
  }
}
```

### Response Field Description

For the top-level fields, see [Response Parameters](#response-parameters). The `data` fields are described as follows:

| Field | Type | Required | Description |
|:---|:---|:---|:---|
| preparation_flag | boolean | Yes | Whether it is ready to power off.<ul><li>false: not ready to power off</li><li>true: ready to power off</li></ul> |
