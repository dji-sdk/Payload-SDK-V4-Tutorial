Payload SDK is a set of open-source payload access SDKs based on the MQTT protocol, designed for development scenarios where self-developed or third-party payloads are integrated into the DJI aircraft platform. Developers can use the C interfaces and reference implementations provided by the SDK to implement business logic in the payload firmware or the onboard computing platform, completing capability integrations such as device authentication and coming online, control interaction, data reporting, and remote upgrade.

Unlike access solutions packaged as binary libraries, this SDK is fully open in both protocol and source code. The entire communication process is transparent, tailorable, and independently portable. The accompanying streamlined runtime library, cross-platform sample library, and pluggable adaptation layer together form a complete payload access development kit.

> Runtime library (Runtime): The core support library provided by the SDK, which encapsulates general capabilities such as MQTT session management, authentication, encoding/decoding, and memory management. It runs together with the payload application, and developers can link and call it directly without implementing the low-level communication logic themselves.

With Payload SDK, developers can:

* Use a unified capability description to define the services, properties, events, and states that the payload provides externally;
* Integrate the SDK on the payload itself (MCU / RTOS) or on the onboard computing platform (Linux) to implement device-side capabilities;
* Perform bidirectional interaction of control commands and data with the platform through a standard MQTT channel;
* Reuse the open, pluggable runtime library without implementing the MQTT protocol stack, authentication, and encoding/decoding themselves.

## Software Framework Overview

The SDK adopts a layered design in which each layer has a single responsibility and clear boundaries. Developers mainly focus on the business implementation at the topmost layer, while the low-level communication is handled by the runtime library.

The responsibilities of each layer are as follows:

* **Application layer**: The developer's business code, which implements the specific capabilities of the payload, such as service handling, status collection, and data processing.
* **SDK interface code**: The C client-side and device-side code provided by the SDK, responsible for opening up the business interface capabilities.
* **Runtime Library**: Manages MQTT sessions, authentication (TLS + HMAC), automatic reconnection and subscription recovery, JSON encoding/decoding, and memory management.
* **Adaptation layer**: Transport (mosquitto / Paho), encryption (OpenSSL / mbedTLS), operating system (POSIX / RTOS), and memory allocation are all replaceable, facilitating integration with existing security solutions and hardware platforms.
* **Platform layer**: Accesses the platform through the MQTT Broker and interacts with the cloud / App.

## Development Process

From an engineering implementation perspective, payload access follows the process below:
1. **Define capabilities**: Define the protocol of the payload's services / properties / events / states.
2. **Integrate the runtime library**: Introduce the runtime library and protocol code into the project, and register the OS / transport / encryption adaptations.
3. **Implement capabilities**: Write the device-side business logic to handle service calls and report status and events.
4. **Configure credentials**: Fill in the App credentials (App ID / Key / License), device SN, and Broker address.
5. **Joint debugging and coming online**: Connect to the Broker to complete authentication, verify the control and data links, and then officially come online.


## Two Deployment Forms

Depending on the runtime location of the SDK, payload development is divided into two deployment forms.

### Payload-Body Development (Embedded MCU / RTOS)

Run the SDK directly on the payload device's embedded controller (such as GD32F527 + FreeRTOS / lwIP / mbedTLS).

* Close to the hardware, small resource footprint, no additional computing power unit required;
* The payload body directly connects to the network and accesses the platform;
* Suitable for payload bodies such as speakers, custom widgets, and sensors.

### Onboard Computing Platform Development (Linux)

Run the SDK on an onboard Linux computing platform (such as Manifold or a general-purpose Linux board, supporting x86_64 / aarch64) (for example, Ubuntu + mosquitto / Paho + OpenSSL).

* Sufficient computing power, facilitating integration of complex business logic and third-party libraries;
* Can carry multi-payload aggregation and collaboration;
* Suitable for scenarios with large data processing volumes or complex business logic.

## The Relationship Between the Two Forms

* **Independent deployment**: Either form—the payload body or the onboard computing platform—can access the platform independently.
* **Collaborative deployment**: The payload body is responsible for perception and execution, and the onboard computing platform is responsible for aggregation, processing, and forwarding. The two collaborate through the onboard link to form a complete payload business system.

```
Payload body (collection / execution)
    ↕ Onboard link
Onboard computing platform (aggregation / processing / scheduling)
    ↕ MQTT
MQTT platform (remote management / data aggregation)
```


## How to Choose a Development Method

| Comparison Item | Payload-Body Development (MCU / RTOS) | Onboard Computing Platform Development (Linux) |
| --- | --- | --- |
| Runtime environment | Embedded real-time system | Onboard Linux (x86_64 / aarch64) |
| Computing resources | Limited | Sufficient |
| Resource footprint | Small | Medium |
| Third-party library integration | Limited | Flexible |
| Typical payloads | Speaker / widget / sensor | Complex business / multi-payload aggregation |
| Applicable scenarios | Hardware body directly connected to the network | High computing power / complex data processing |

Selection recommendations:

* Resource-constrained, single-function, cost-sensitive → Payload-body development (MCU / RTOS)
* High computing power requirements, complex business, need to integrate third-party libraries → Onboard computing platform development (Linux)
* Multi-payload collaboration / unified gateway → Onboard computing platform aggregation + payload-body access

> The above is common engineering experience. The actual selection is also affected by factors such as payload form, function complexity, cost, and team experience.
